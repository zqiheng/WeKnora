## 1. 分块的三层策略（Tier）

分块入口 `chunker.Split(text, cfg)`（`strategy.go:34`）按 `Strategy` 字段选择一条「**降级链（tier chain）**」，逐个尝试，当前 tier 结果被校验器拒绝时就降级到下一个：

| Strategy | tier 链 | 说明 |
| --- | --- | --- |
| `heading` | `[TierHeading, TierLegacy]` | 先按标题切，无结构则降级递归 |
| `heuristic` | `[TierHeuristic, TierLegacy]` | 先按启发式边界切，无结构则降级递归 |
| `recursive`/`legacy`/ 空 | `[TierLegacy]` | 只用递归切分（历史默认） |
| `auto` | 由 profiler 决定 | 先剖析文档结构，自动选 heading / heuristic / recursive |

```text
Split(text, cfg)
  ├─ ensureDefaults（补默认值）
  ├─ resolveChainWithProfile（选 tier 链）
  └─ 依次 runTier，ValidateChunks 校验通过则返回
        ├─ Tier 1 heading   → splitByHeadings
        ├─ Tier 2 heuristic → splitByHeuristics
        └─ Tier 3 legacy    → SplitText（递归切分，最终兜底）
```

**关键点**：

- 每层切分后都有 `ValidateChunks` 校验（分块数、大小、位置不变量），不合格就降级；
- **legacy 递归切分是最终兜底**，任何文档都能被它切开，保证不失败。

## 2. 递归切分 SplitText（Tier 3 兜底）

文件：`splitter.go:272`（`SplitText`）

这是最基础的切分算法，三步：

### 2.1 找到保护区间（protected spans）

先扫描全文，找出**不能切开**的内容（见 §5），标记为保护区间。

### 2.2 按分隔符递归切分非保护区

`buildUnitsWithProtection`：对保护区间之间的普通文本，按 `Separators` 优先级递归切分：

```text
默认 Separators = ["\n\n", "\n", "。"]
        ↓ 优先级从高到低
先按 "\n\n"（段落）切 → 超长的段落再按 "\n"（行）切 → 再按 "。"（中文句号）切
```

保护区间（代码块、表格、公式等）作为**原子单元**整体保留，不被切开。超大的保护区间（> 7500 字符）会被强制在换行/空格处拆开。

### 2.3 合并单元 + overlap

`mergeUnits`把切出来的单元合并成 chunk，直到达到`ChunkSize`，然后保留 `ChunkOverlap` 的上下文重叠：

```text
单元流 → 累加到 chunkSize 上限 → flush 一个 chunk
                                  ↘ 保留 overlap 个字符作为下一个 chunk 的开头
```

**overlap 的意义**：答案可能被切在 chunk 边界上，overlap 让边界两侧的内容有重叠，保证边界附近的信息能被完整召回。

**合并时的额外处理**：

- **表格表头前置**（`header_tracker.go`）：Markdown 表格被切开时，每个新 chunk 都前置当前表格的表头（表头是受保护单元，但切分后表体分散到多个 chunk，需要给每个 chunk 补上表头上下文）；
- **表格边界 flush**：遇到新表格时先 flush 当前 chunk，避免把上一张表的内容和下一张表合并。

## 3. 标题感知切分（Tier 1）

文件：`heading_splitter.go:32`（`splitByHeadingsImpl`）

对**有标题结构**的文档（Markdown 技术文档），按标题层级切分：

### 3.1 算法

1. `profile.DominantHeadingLevel()`找到文档的**主导标题层级**（如`##` 二级标题为主）；
2. `findHeadingBoundaries`找到所有`level <= 主层级` 的标题作为**节边界**；
3. 遍历每个节：
   - **节内容 ≤ ChunkSize** → 整个节作为一个 chunk，面包屑（breadcrumb）作为 `ContextHeader`；
   - **节内容 > ChunkSize** → 委托给 legacy `SplitText` 做内部细分，每个子 chunk 拿到**最深活跃标题**的面包屑。

### 3.2 面包屑（Breadcrumb）

`heading_hierarchy.go` 维护一个**标题层级栈**，切分时记录当前活跃的标题路径：

```text
# 第一章
## 1.1 背景
### 1.1.1 动机          ← 这里的 chunk 的面包屑 = "# 第一章\n## 1.1 背景\n### 1.1.1 动机"
```

面包屑存在 `Chunk.ContextHeader`（**独立于 Content**，不破坏「Content 长度 == End-Start」的位置不变量），在 embedding 时前置到正文前（见 §7）。

> 关键：标题切分让每个 chunk 自带「它在文档里的位置」上下文，召回片段不再是孤立的一段文字，而是「知道自己在哪个章节」。

## 4. 启发式切分（Tier 2）：语义感知 + 段落感知

文件：`heuristic_splitter.go:34`（`splitByHeuristicsImpl`）+ `patterns.go`（语义模式）

对**无 Markdown 标题但有结构语义边界**的文档（纯文本、扫描件转文本、PDF 转文本），按「语义/结构信号」切分。这是 WeKnora 的**语义感知切片**核心。

### 4.1 七类语义边界（patterns.go，带优先级）

`BoundaryPriority` 给每类边界打分，越高越强（同位置多边界时保留最强的）：

| 优先级 | 语义边界 | 正则示例 |
| --- | --- | --- |
| 100 | 换页符 `\f` | PDF 转文本的页分隔 |
| 90 | 编号章节 | `1. Intro`、`2.3 Methods`、`IV. Results`、`2.2.1 用户与权限` |
| 85 | 多语言章节标记 | 德语 `Kapitel/Abschnitt/Teil`、英语 `Chapter/Section/Part`、中文 `第X章/第X节` |
| 70 | 全大写短行 | 无 Markdown 标题的章节标题 |
| 60 | 视觉分隔线 | `---`/`===`/`***`/`___` |
| 50 | 页脚 | `Seite X von Y` / `Page X of Y` |
| 40 | 连续空行 | `\n{3,}` 硬分段（**段落感知**） |

**段落感知**：最后一项「连续空行 `\n{3,}`」就是段落感知——3 个以上连续换行视为硬分段（区别于递归切分的 `\n\n` 双换行段落，见 §2.2）。

### 4.2 边界识别算法（findHeuristicBoundaries）

1. **逐行扫描**，用正则匹配上述语义边界，记录 `(rune 偏移, 优先级)`；
2. **代码围栏感知**：跳过 ``` 围栏内的行（`inFence` 标记），避免把代码里的 `1. Foo`、`Chapter X` 误判为章节边界；
3. **丢弃保护区间内的边界**：边界落在表格/代码块/公式内部时丢弃（不切原子内容，见 §5）；
4. **排序去重**：按位置升序，同位置保留最高优先级。

### 4.3 贪心 bin-packing

识别出边界后，用**贪心装箱**把边界之间的 block 累积成 chunk：

```text
边界 [0, b1, b2, ..., 末尾哨兵]
  └─ 从 0 开始，逐个边界推进：
       若「当前 block + 下一个 block」≤ ChunkSize → 继续累积
       否则 → flush 当前 chunk，从下一边界重新开始
```

- 累积 block 直到下一个 block 会超 `ChunkSize`，才 flush 一个 chunk（保证 chunk 尽量贴合语义边界、又不超过大小上限）；
- 单个 block 仍超 `ChunkSize` → 递归委托 legacy splitter 细分（超大块递归降级）。

### 4.4 多语言语义

- **章节标记按语言**：`ChapterPatternsForLangs(langs)` 按语言提示返回对应正则（德/英/中），未知语言返回全部；
- **句子级分隔符**：`SentenceSeparators(lang)` 按语言返回（中文 `。！？；`、英文 `. ! ? ;`），用于超大块的细粒度子切分。

## 5. 保护模式：哪些内容不切开

`splitter.go:118`的`protectedPatterns` 定义了**绝对不能切开**的内容：

| 保护内容 | 正则意图 |
| --- | --- |
| LaTeX 块公式 `$$...$$` | 数学公式不能被切开 |
| Markdown 图片 `![...](...)` | 图片引用是整体 |
| Markdown 链接 `[...](...)` | 链接文本和 URL 不能分离 |
| 表格（表头+分隔行） | 表格结构不能被破坏 |
| 围栏代码块 ```` ```...``` ```` | 代码块是整体 |
| 行内代码 `` `...` `` | 行内代码是整体 |

**为什么保护**：这些内容一旦被切开，语义就破坏了（公式缺一半、表格没了表头、代码块断成两截），检索召回时会得到残缺片段。

## 6. 大小块（父-子分块）详解

这是「大小块」的完整机制。入口：`chunker.SplitParentChild(text, parentCfg, childCfg)`（`strategy.go:135`）。

> **格式无关**：父子块是知识库级开关（`ChunkingConfig.EnableParentChild`），作用在「统一 Markdown 中间态」上，**不区分文件格式**。docx / pdf / ppt / xlsx / md / epub … 解析成 Markdown 后统一进入 `SplitParentChild`（文件/URL 导入 `knowledge_process.go:3533`、手动内容 `knowledge_create.go:1281`），没有任何按 `fileType` 的特判。xlsx 也不例外——它的「行级结构化切片」是解析层的事（见《表格切片与表头识别.md》），解析完的文本在分块层照样走父子块。

### 6.1 大小块的配置（DeriveParentChildConfigs）

`strategy.go:220` 从基础配置派生出**父块（大块）**和**子块（小块）**两套配置：

```go
parent = SplitterConfig{
    ChunkSize:    parentSize,        // 默认 4096（大块）
    ChunkOverlap: base.ChunkOverlap, // 默认 80
    Strategy:     base.Strategy,
}
child = SplitterConfig{
    ChunkSize:    childSize,         // 默认 384（小块）
    ChunkOverlap: childSize / 5,     // ≈ 77
    Strategy:     base.Strategy,
    TokenLimit:   base.TokenLimit,   // token 上限只作用于子块
}
```

| 维度 | 大块（父块） | 小块（子块） |
| --- | --- | --- |
| 大小 | `ParentChunkSize`（默认 4096 字符） | `ChildChunkSize`（默认 384 字符） |
| 用途 | 提供**完整上下文** | 用于**向量匹配** |
| 是否索引 | ❌ 不索引（存 DB 供上下文展开） | ✅ 索引（embedding） |
| ChunkType | `parent_text` | `text` |

### 6.2 切分算法（SplitParentChild）

```text
SplitParentChild(text, parentCfg, childCfg)
  ├─ Split(text, parentCfg)  → 先按大块配置切出父块
  └─ 对每个父块：
        Split(parent.Content, childCfg)  → 按小块配置再切成子块
        ├─ 子块的 Start/End 累加父块偏移（保持全局位置）
        └─ ContextHeader = mergeBreadcrumbs(父面包屑, 子面包屑)
```

`mergeBreadcrumbs` 合并父/子两层面包屑（去掉重复行），让子块的 embedding 上下文同时带着父块的章节信息和子块的细粒度标题。

### 6.3 为什么用大小块（核心动机）

```text
文档
 ├─ 父块 A（4096 字符，完整上下文）── 存 DB，不索引
 │   ├─ 子块 A1（384 字符）── embedding 索引
 │   ├─ 子块 A2（384 字符）── embedding 索引
 │   └─ 子块 A3（384 字符）── embedding 索引
 └─ 父块 B（4096 字符）...
```

检索时：**用小子块匹配，返回大父块内容**。

这解决了 RAG 检索的经典两难：

- **块太大** → 召回不精确（一个 4096 的块包含太多无关内容，语义被稀释）；
- **块太小** → 上下文断裂（384 字符说不清一件事，答案跨块就漏）。

大小块让「检索的精度」和「喂给 LLM 的完整性」解耦：小块的向量精确命中，大块的正文提供完整上下文。

> 对应实现：`processChunks` 里父块只写 DB（`ChunkType = parent_text`），子块写 DB + 建向量索引；检索命中子块后，`merge.go`的`resolveParentChunks` 把子块解析成父块正文喂给 LLM。

### 6.4 父块的定位：纯上下文块，不参与索引与富化

父块（`parent_text`）在系统里的定位**非常单一**：它**只参与「检索时的子块 → 父块上下文引用」**，不参与任何其它逻辑：

| 逻辑 | 父块是否参与 |
| --- | --- |
| embedding 向量计算 / 写入向量库 | ❌ 不参与 |
| 关键词索引（BM25/全文） | ❌ 不参与 |
| 问题生成（question generation） | ❌ 不参与（只针对 `ChunkTypeText`） |
| 知识图谱抽取（entity/relation） | ❌ 不参与（`graphChunkCount = len(textChunks)`） |
| 文档摘要 | ❌ 不参与（`sortChunksForSummary` 用 textChunks） |
| **检索时的「子块 → 父块」上下文引用** | ✅ 唯一用途 |
| 克隆/移动数据复制 | ✅ 仅数据搬运 |

**代码依据**：

- `types/chunk.go:18` 注释直接声明：*"ChunkTypeParentText 表示父子分块策略中的父文本 Chunk（仅用于上下文，不参与向量索引）"*；
- `processChunks`（`knowledge_process.go:445`）索引循环只遍历 `textChunks`（`ChunkTypeText`），父块不进 `indexInfoList`——所以既不进向量库、也不进关键词库；
- 父块只通过 `CreateChunks` 写 DB（供检索时反查）。

**两条「父块加载」路径**（都是「命中子块 → 加载父块正文」，不是「父块被检索命中」）：

| 路径 | 位置 | 机制 |
| --- | --- | --- |
| Chat 流水线 | `merge.go` `resolveParentChunks` | `HybridSearch` 传 `SkipContextEnrichment=true`，父块加载在 merge 阶段完成 |
| Agent 工具 / 搜索 API | `knowledgebase_search_results.go` `collectEnrichmentChunkIDs` | `SkipContextEnrichment=false` 时，检索到子块后额外收集 `ParentChunkID`、标记 `MatchTypeParentChunk`，反查 DB 加载父块内容 |

## 7. embedding 输入：面包屑 + 标题 + 正文

`Chunk.EmbeddingContent()`（`splitter.go:43`）：

```go
func (c Chunk) EmbeddingContent() string {
    body := strings.TrimSpace(c.Content)
    if c.ContextHeader == "" {
        return body
    }
    return c.ContextHeader + "\n\n" + body   // 面包屑前置
}
```

在索引阶段（`processChunks`），最终 embedding 输入再叠加**文档标题**（最外层）：

```text
embedding 输入 = 文档标题 + ContextHeader（标题面包屑） + chunk 正文
```

**为什么**：问句式 query（"如何配置？"）和陈述式 chunk（"配置方法如下..."）语义有 gap，把「标题 + 章节面包屑」前置，让 chunk 的向量更贴近用户「带着上下文」的提问，提升语义对齐（这是检索质量的关键细节，见《检索质量深度剖析.md》）。

## 8. 参数速查

### 8.1 默认值

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `ChunkSize` | 512 | 分块字符数（≈100-130 英文 token / ≈300 中文 token） |
| `ChunkOverlap` | 80 | 重叠字符数（≈15% ChunkSize） |
| `Separators` | `["\n\n", "\n", "。"]` | 递归分隔符优先级 |
| `ParentChunkSize` | 4096 | 父块（大块）大小 |
| `ChildChunkSize` | 384 | 子块（小块）大小 |
| `Strategy` | auto/heading/heuristic/recursive/legacy | 切分策略 |
| `TokenLimit` | 0（= 用 ChunkSize 按字符） | 按 token 近似上限 |

### 8.2 调优建议（来自代码注释）

| 场景 | 建议 |
| --- | --- |
| FAQ / 原子内容 | `ChunkSize` 200-400，`Overlap` 0 |
| 叙述 / 论证性文档 | `ChunkSize` 1000-2000，`Overlap` 150-200 |
| 结构化 Markdown | `Strategy=heading` |
| 纯文本 / 扫描件 | `Strategy=heuristic` |
| 长文档需要完整上下文 | 开启 `EnableParentChild` |

### 8.3 硬性约束（代码内保护）

- **绝对上限 7500 字符**：任何单个 chunk（含受保护内容）超过 7500 会被强制切分；
- **Overlap 上限 ChunkSize/2**：防止 overlap 过大导致 chunk 近乎重复；
- **保护模式**：公式/图片/链接/表格/代码块不切开。
