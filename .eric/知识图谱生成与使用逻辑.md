# WeKnora 知识图谱：生成与使用逻辑

> 本文梳理 WeKnora 自带的「知识图谱」功能（基于 **Neo4j** 的实体-关系图谱）的技术实现原理与核心逻辑，覆盖生成（实体/关系抽取 → 入库）与使用（检索时查图谱补充上下文）两条链路。
>
> 核心思想：文档入库时用 LLM 抽取**实体 + 关系**存入 Neo4j；对话时从 query 抽取**实体**，查图谱找到相关 chunk，补充到检索结果中，实现「图谱增强 RAG」。
>
> 代码基准：`internal/`（Go 后端）。开启方式：环境变量 `NEO4J_ENABLE=true` + 知识库设置里启用「实体抽取/关系抽取」。

## 1. 总体架构

知识图谱功能是「**图谱增强 RAG**」：把文档的结构化知识（实体及关系）抽取到图数据库，检索时用图谱做**语义补召回**。

```text
┌────────────────────────── 生成（离线异步） ──────────────────────────┐
│  文档入库 → 分块 → 每 chunk 入队 graph 抽取任务                        │
│      → ChunkExtractService（LLM 抽实体/关系）                          │
│      → Neo4jRepository.AddGraph（写 Neo4j）                           │
└──────────────────────────────────────────────────────────────────────┘

┌────────────────────────── 使用（在线检索） ──────────────────────────┐
│  对话 query                                                          │
│    → PluginExtractEntity（LLM 抽 query 实体）                         │
│    → PluginSearchEntity（Neo4j SearchNode 查图谱）                    │
│    → 关联 chunk 并入 SearchResult（MatchType=graph）                  │
└──────────────────────────────────────────────────────────────────────┘
```

**两条链路共用同一个核心组件 `Extractor`**（LLM 结构化抽取器），区别只在输入：

- 生成侧：抽取 `chunk.Content`（文档片段）；
- 使用侧：抽取 `query`（用户问题）。

> **注**：`internal/application/service/graph.go`里还有一个`GraphBuilder`（`BuildGraph`/`GetRelationChunks`/`GetIndirectRelationChunks`，基于 `types.Entity`/`types.Relationship` 的 chunk 级关系图）。它**未接线到 DI 容器**（`NewGraphBuilder` 无任何调用方、`GetRelationChunks` 也无调用方），属于遗留/未启用的实现，不是当前生效的知识图谱。当前生效的只有 Neo4j 实体关系图谱。

## 2. 配置：ExtractConfig 与 Neo4j 环境变量

### 2.1 环境变量（全局开关）

```env
NEO4J_ENABLE=true
NEO4J_URI=bolt://neo4j:7687
NEO4J_USERNAME=neo4j
NEO4J_PASSWORD=your_password
# 可选 NEO4J_DATABASE=neo4j
```

`NEO4J_ENABLE != "true"` 时，所有图谱逻辑都是 no-op（生成任务不入队、查询跳过）。

### 2.2 ExtractConfig（知识库级抽取配置）

`internal/types/knowledgebase.go:637`，存在知识库上，控制「抽哪些实体类型、哪些关系类型」：

```go
type ExtractConfig struct {
    Enabled            bool             // 是否开启实体/关系抽取
    Text               string           // few-shot 示例文本
    Tags               []string         // 关系类型（约束 LLM 只能输出这些关系）
    Nodes              []*GraphNode     // few-shot 示例实体
    Relations          []*GraphRelation // few-shot 示例关系
    CustomInstructions string           // 领域自定义抽取指导
}
```

- `Tags`（关系类型）会作为**约束**注入 prompt，LLM 只能抽取白名单内的关系类型；
- `Nodes`/`Relations`/`Text` 作为 **few-shot 示例**注入 prompt，引导抽取格式；
- `CustomInstructions` 追加领域指导（如「医药领域的实体是疾病/药物/靶点」）。

### 2.3 行业/领域的维护：无行业模板库，靠「KB 级三旋钮」

WeKnora **没有「行业/领域」的一等公民概念**——没有内置行业模板库、没有 schema 级定制、没有实体类型分类器。不同领域的差异，全靠**每个知识库一份 `ExtractConfig`**，而且**纯 prompt 层定制**。

**系统固定 vs 下放给配置**：

- **系统固定住**：输出协议——结构化 JSON 格式、关系类型必须来自白名单、实体用 `name`+`attributes` 建模（§4.6）；
- **下放给配置**：什么是实体、哪些关系类型、领域术语是什么、抽取粒度——这些业务语义全部交给 KB 配置。

三个旋钮，正好对应三种领域维护手法：

| 旋钮 | 字段 | 作用 | 金融行业示例 |
| --- | --- | --- | --- |
| 关系类型词汇表 | `Tags` | 白名单约束 LLM 只能抽这些关系类型（替换默认 `["Author","Alias"]`） | `["股东","子公司","竞争对手","并购","供应商"]` |
| 领域 few-shot | `Text`+`Nodes`+`Relations` | 给一条该领域样例，引导格式与粒度 | 一段「某公司收购某公司」的样例，实体带行业属性、关系类型用上面的词表 |
| 领域指导指令 | `CustomInstructions` | 追加一段领域抽取说明（≤4000 字符，`prompt_instructions.go` 校验） | 「医药领域的实体是疾病/药物/靶点，关系聚焦适应症、作用机制、相互作用」 |

**三层覆盖，最细到单次上传**：

```text
config.yaml 默认模板（description + tags + 通用文学示例）
   → 被 KB 级 ExtractConfig 覆盖
        → 被 单次上传的 KnowledgeProcessOverrides 再覆盖（ResolveProcessConfig）
```

拼接点在 `extract.go:341-352`（§4.3「关键机制 3」已展开）。

**权衡**：

- 好处：灵活，一个 KB 一套领域词汇表，互不干扰，改动只影响本库；
- 代价：**没有开箱即用的行业模板**，每个新领域都要用户自己写 `Tags` + few-shot + `CustomInstructions`；领域词汇的准确率完全取决于用户 prompt 写得好不好。

> ⚠️ 别把「实体类型」和「关系类型」搞混：live 路径的实体**没有**类型枚举（实体 = `name` + `attributes`），有类型约束的只有**关系**（`Tags` 白名单）。那套「Person/Organization/Location 等 11 类实体类型」在 `graph_extraction.yaml`，是**死代码**（见 §4.1）。

## 3. 生成流程：异步抽取任务

### 3.1 入队（NewChunkExtractTask）

文件：`internal/application/service/extract.go:89`

文档入库、分块后，**每个 chunk 入队一个图抽取任务**：

```go
func NewChunkExtractTask(...) (bool, error) {
    if strings.ToLower(os.Getenv("NEO4J_ENABLE")) != "true" {
        return false, nil   // Neo4j 未开启，直接跳过（no-op）
    }
    task := asynq.NewTask(types.TypeChunkExtract, payload,
        asynq.Queue(types.QueueGraph),   // 独立 graph 队列
        asynq.MaxRetry(3),               // 最多重试 3 次
        asynq.Timeout(30*time.Minute))   // 30 分钟超时
    _, err := client.Enqueue(task)
    ...
}
```

要点：

- **每 chunk 一个任务**——图抽取是最昂贵的富化 fan-out（每 chunk 一次 LLM 调用）；
- 任务 payload 携带 `TenantID / ChunkID / ModelID / KnowledgeID / Attempt / ChunkIndex`；
- 走**独立 `graph` 队列**（与 summary/multimodal/postprocess 队列隔离）。

### 3.2 任务处理（ChunkExtractService.Handle）

文件：`internal/application/service/extract.go:223`，核心流程：

1. **解析 payload**，注入 requestID / tenant / chunkID 上下文。
2. **幂等/取消保护**：
   - `attemptSuperseded`：较新的重传/编辑已取代本任务 → 跳过（避免递减新 attempt 的计数器）；
   - `knowledge.ParseStatus == Cancelled/Deleting` → 跳过（图抽取是最贵的一步，取消时立即短路）。
3. **读 chunk 内容**（`chunkRepo.GetChunkByID`）。
4. **读 KB → 解析抽取配置**（`ResolveProcessConfig(kb, overrides).ExtractConfig`），`!Enabled` 则跳过。
5. **取 chat model**（`GetChatModel`）。
6. **构建 prompt 模板**（`PromptTemplateStructured`）：系统描述 + 自定义指导 + 关系类型 tags + few-shot 示例。
7. **执行抽取**：`chatpipeline.NewExtractor(chatModel, template).Extract(ctx, chunk.Content)`→ 得到`GraphData`（nodes + relations）。
8. **关联 chunk**：每个 `node.Chunks = [chunk.ID]`（实体 → 来源 chunk 的映射，这是检索时反查 chunk 的关键）。
9. **写图**：`graphEngine.AddGraph(NameSpace{KB, Knowledge}, []*GraphData{graph})` → Neo4j。
10. **收尾**：`finalizeSubtaskDetached`递减父 knowledge 的`pending_subtasks_count`（保证 knowledge 状态机的最终化）。

> 关键设计：`node.Chunks` 把「实体」和「它出现的 chunk」绑定。检索时查到实体，就能拿到它所在的 chunk，把 chunk 正文喂给 LLM。

## 4. 抽取器：LLM 结构化抽取

文件：`internal/application/service/chat_pipeline/extract_entity.go`

### 4.1 两套模板系统（先厘清，避免踩坑）

代码里有**两套实体抽取 prompt 模板**，当前真正生效的只有一套：

| 系统 | 模板来源 | 抽取方式 | 输出格式 | 状态 |
| --- | --- | --- | --- | --- |
| **A. 生效的 Neo4j 路径** | `config.yaml` 的 `extract.extract_graph` / `extract.extract_entity` | **单次调用**同时抽实体+关系（或只抽实体） | `{"entity":..., "entity_attributes":[...]}` / `{"entity1":..., "entity2":..., "relation":...}` | ✅ 生效 |
| **B. 遗留的 graph.go** | `config/prompt_templates/graph_extraction.yaml`（`default_extract_entities` / `default_extract_relationships`） | **两步**：先抽实体（`title/type/description`），再抽关系（`source/target/description/strength`） | 实体带 `type`（11 类枚举）+ `description`；关系带 `strength`（5-10） | ❌ 未接线（dead code） |

**怎么区分**：

- `config.yaml` 的 `conversation.extract_entities_prompt_id: "default_extract_entities"` 指向 `graph_extraction.yaml`——但这是给 **`graph.go` 的 `GraphBuilder`** 用的（`b.config.Conversation.ExtractEntitiesPrompt`）；
- 而 `graph.go` 的 `NewGraphBuilder` **全仓库无调用方**，所以 `graph_extraction.yaml` 那套「11 类实体枚举 + 关系强度 5-10」的 prompt **实际不生效**；
- **真正生效**的是 `config.ExtractManager.ExtractGraph` / `ExtractEntity`，来自 `config.yaml` 的 `extract` 段（不是独立 prompt 文件）。

### 4.2 模板来源与结构

`config.ExtractManagerConfig`（`internal/config/config.go:460`）：

```go
type ExtractManagerConfig struct {
    ExtractGraph  *types.PromptTemplateStructured `yaml:"extract_graph"`
    ExtractEntity *types.PromptTemplateStructured `yaml:"extract_entity"`
}
```

- `ExtractGraph`：生成侧（文档 chunk → 实体+关系）用；
- `ExtractEntity`：查询侧（query → 实体）用。

`PromptTemplateStructured` 三要素（`internal/types/extract_graph.go`）：

```go
type PromptTemplateStructured struct {
    Description string      // 任务描述（含 %s 占位符，注入关系类型白名单）
    Tags        []string    // 关系类型白名单
    Examples    []GraphData // few-shot 示例
}
```

### 4.3 生成侧 extract_graph 模板

`extract.extract_graph` 模板（`config.yaml:50`）：

```text
## Step 1: Entity Extraction and Attribute Enrichment
1. 抽取核心实体（按叙述顺序 / 关联紧密程度）
2. 富化实体属性（补全文本中明确提到的属性）

## Step 2: Relationship Extraction and Verification
1. 识别关系类型：只从指定的关系列表中选择。允许的关系类型：%s   ← Tags 注入
2. 抽取有效关系（基于实体和属性，杜绝虚构）
3. 明确关系主体（标注两个关联实体，避免主体混淆）
4. 补充关系相关属性

tags: ["Author", "Alias"]   ← 默认关系类型白名单
examples: [Romeo and Juliet 示例]
```

**关键机制 1 —— 关系类型白名单（`%s` 注入）**：`QAPromptGenerator.System()`（`extract_entity.go:244`）把 `Tags` 序列化为 JSON 数组，填入 `Description` 的 `%s` 占位符：

```go
if len(qa.Template.Tags) == 0 {
    promptLines = append(promptLines, qa.Template.Description)
} else {
    tags, _ := json.Marshal(qa.Template.Tags)
    promptLines = append(promptLines, fmt.Sprintf(qa.Template.Description, string(tags)))
}
```

即 LLM 看到的是「允许的关系类型：`["Author","Alias"]`」，只能从白名单里选，不能自造。

**关键机制 2 —— few-shot 示例**：`Examples` 里的 Romeo and Juliet 示例会被渲染成：

````text
# Examples
Q: <示例文本>
A: ```json
   [{"entity":"Romeo and Juliet","entity_attributes":["A tragedy by William Shakespeare"]},
    ...
    {"entity1":"Romeo and Juliet","entity2":"William Shakespeare","relation":"Author"}]
   ```
````

这同时**定义了输出格式**（`entity` / `entity_attributes` / `entity1` / `entity2` / `relation`）和**抽取粒度**（什么是实体、什么是属性、什么是关系）。

**关键机制 3 —— 知识库级覆盖（ExtractConfig）**：生成侧实际构建模板时（`extract.go:341`），**知识库的 `ExtractConfig` 覆盖默认模板**：

```go
template := &types.PromptTemplateStructured{
    Description: types.AppendCustomPromptInstructions(
        s.template.Description, extractCfg.CustomInstructions, "graph_extraction"),
    Tags:     extractCfg.Tags,      // ← 覆盖默认的 Author/Alias
    Examples: []types.GraphData{{   // ← 覆盖默认的 Romeo 示例
        Text:     extractCfg.Text,
        Node:     extractCfg.Nodes,
        Relation: extractCfg.Relations,
    }},
}
```

配置层级：`config.yaml 默认模板（description + tags + example）` → 被 `知识库 ExtractConfig（Tags/Nodes/Relations/Text/CustomInstructions）` 覆盖。所以「抽哪些关系类型」「用什么样的 few-shot 示例」「有没有领域指导」都是**知识库级可配置**的。

### 4.4 查询侧 extract_entity 模板

`extract.extract_entity` 模板（`config.yaml:91`）与生成侧**不同**——只抽实体名，不抽属性和关系：

```text
基于用户问题，完成关键信息抽取：
1. 分析逻辑关联：识别核心逻辑关系，标注逻辑类型
2. 抽取关键实体：精确抽取、分类，不遗漏不冗余
3. 实体排序：按与主题的关联紧密程度排序

examples: [Romeo and Juliet 示例，node 只有 name，无 attributes]
```

输出格式只有 `node: [{name: ...}]`，无 `entity_attributes`、无 `relation`。**用途**：查询侧只需要「实体名列表」，用来查 Neo4j（`SearchNode` 的 `n.name CONTAINS nodeText`），不需要属性和关系。

### 4.5 Extractor（抽取器）与调用

```go
type Extractor struct {
    chat     chat.Chat                        // LLM 客户端
    formater *Formater                        // 输出格式化/解析
    template *types.PromptTemplateStructured  // few-shot 模板
    chatOpt  *chat.ChatOptions                // temperature 0.3, maxTokens 4096, thinking=false
}
```

`Extractor.Extract(ctx, content)`：

1. `QAPromptGenerator.Render` 生成 prompt（system + user）；
2. 调 `chat.Chat`（temperature 0.3，低温度保证结构化输出的稳定性）；
3. `Formater.ParseGraph` 解析 LLM 输出为 `GraphData`。

- **temperature 0.3**：结构化抽取用低温度，减少格式漂移；
- **thinking=false**：关思考链，直接输出 JSON。

### 4.6 输出解析（Formater.ParseGraph）

LLM 输出的 JSON 数组，`Formater.ParseGraph`（`extract_entity.go:420`）按字段区分节点/关系：

```go
switch {
case group[nodePrefix] != nil:  // 有 "entity" 字段 → 节点
    nodes = append(nodes, &GraphNode{
        Name:       group["entity"],
        Attributes: group["entity_attributes"],  // 可选
    })
case group[relationSource] != nil && group[relationTarget] != nil:  // 有 entity1/entity2 → 关系
    relations = append(relations, &GraphRelation{
        Node1: group["entity1"],
        Node2: group["entity2"],
        Type:  group["relation"],
    })
}
```

解析流程（含兜底与重建）：

1. **围栏剥离**（`extractContent`）：从 LLM 输出提取 ```` ```json ```` / ```` ```yaml ```` 围栏内的内容；
2. **兜底**（`stripFencesAndExtract`）：截断输出（有开围栏无闭围栏）、无围栏但有可识别 JSON（`extractJSONLike` 找最外层 `{...}`/`[...]`，尊重字符串字面量里的括号）；
3. **JSON 解析**为 node/relation 列表；
4. **重建图**（`rebuildGraph`）：同名 node 去重 + 合并 attributes、自环 relation（`Node1 == Node2`）丢弃、relation 引用了不存在的实体 → 自动补建 node（避免悬空关系）。

> 这个「健壮解析 + 重建」是 LLM 结构化抽取的工程关键：LLM 输出常有围栏缺失、截断、重复实体、自环，需要兜底和去重。

**一句话总结**：实体抽取 = 低温度 LLM 调用 + few-shot 结构模板 + 关系类型白名单 + 健壮 JSON 解析。

## 5. 存储：Neo4j APOC 写入

文件：`internal/application/repository/retriever/neo4j/repository.go`

### 5.1 Label 设计

`NewNeo4jRepository`里`nodePrefix = "ENTITY"`。节点 label = `ENTITY` + 知识库 ID + 知识 ID（去掉连字符）：

```go
func (n *Neo4jRepository) Labels(namespace types.NameSpace) []string {
    // 每个 label 加 "ENTITY" 前缀，且去掉 "-"
    // 例：ENTITY<KB_ID>、ENTITY<KNOWLEDGE_ID>
}
```

**多级 label 实现命名空间隔离**：同一实体名在不同知识库/文档中互不干扰。

### 5.2 写节点（apoc.merge.node）

```cypher
UNWIND $data AS row
CALL apoc.merge.node(row.labels, {name: row.name, kg: row.knowledge_id}, row.props, {}) YIELD node
SET node.chunks = apoc.coll.union(node.chunks, row.chunks)
RETURN distinct 'done'
```

- `apoc.merge.node`：按 `(name, kg)` 唯一键**幂等合并**（同名实体不重复建节点）；
- `apoc.coll.union`：**累加**关联的 chunk 列表（一个实体可能出现在多个 chunk）。

### 5.3 写关系（apoc.merge.relationship）

```cypher
UNWIND $data AS row
CALL apoc.merge.node(row.source_labels, {name: row.source, kg: row.knowledge_id}, {}, {}) YIELD node as source
CALL apoc.merge.node(row.target_labels, {name: row.target, kg: row.knowledge_id}, {}, {}) YIELD node as target
CALL apoc.merge.relationship(source, row.type, {}, row.attributes, target) YIELD rel
```

- 关系类型 = 抽取出的 `rel.Type`（如 `depends_on`/`uses`/`contains`）；
- 先确保 source/target 节点存在，再合并关系。

### 5.4 节点属性

| 属性 | 含义 |
| --- | --- |
| `name` | 实体名 |
| `kg` | 知识 ID（唯一键之一，用于隔离） |
| `chunks` | 关联的 chunk ID 列表（检索时反查 chunk） |
| `attributes` | 实体属性列表 |

### 5.5 删除（DelGraph）

用 `apoc.periodic.iterate` 分批删除（先删关系、再删节点，`batchSize=1000`，`parallel=true`），用于知识删除/重新解析时清空旧图谱。

### 5.6 隔离设计：知识库级 label + 文档级 kg 合并键

图库的隔离是**两层**的，粒度不同：

| 层 | 机制 | 字段 | 作用 |
| --- | --- | --- | --- |
| 知识库级 | 节点 label | `ENTITY<KB_ID>` | 把同一 KB 的实体归组（用于 KB 级查询） |
| 文档级 | 节点 label + 合并键 | `ENTITY<Knowledge_ID>` + `kg` 属性 | 真正的隔离粒度：同名实体跨文档是不同节点 |

**关键点**：`apoc.merge.node` 的合并键是 `{name, kg}`，`kg = namespace.Knowledge`（**文档 ID，非 KB ID**）。因此：

- **同一文档内**：同名实体合并（`chunks` 累加）——一个实体出现在多个 chunk 时只建一个节点；
- **跨文档（即使同一 KB）**：同名实体是**不同的节点**（`kg` 不同）。

所以准确说：**隔离粒度是「文档级」（kg），「知识库级」通过 `ENTITY<KB_ID>` label 实现分组查询**。这比单纯的 KB 级隔离更细——同一个 KB 里两个不同文档都提到「Docker」，会得到两个独立的 Docker 节点，各自绑定自己的 chunk。

## 6. 使用流程：RAG 流水线中的图谱查询

对话时，图谱检索分两步，**都与 `CHUNK_SEARCH`（向量/关键词检索）并行**。

### 6.1 第一步：从 query 抽取实体（PluginExtractEntity）

文件：`internal/application/service/chat_pipeline/extract_entity.go`（`QUERY_UNDERSTAND` 阶段）

`OnEvent` 流程：

1. `NEO4J_ENABLE != true` → 跳过；
2. 收集 `chatManage.KnowledgeBaseIDs`+`KnowledgeIDs`（含共享 KB 文档）；
3. 批量加载 KB，**筛出 `ExtractConfig.Enabled` 的 KB**（`EntityKBIDs`）；
4. 用 `Extractor.Extract(query)` 从用户问题中抽实体；
5. `chatManage.Entity = 实体名列表`，`chatManage.EntityKBIDs = 开启图谱的 KB`。

> 复用生成侧同一个 `Extractor`，但输入是 query（不是 chunk）。

### 6.2 第二步：查图谱找相关 chunk（PluginSearchEntity）

文件：`internal/application/service/chat_pipeline/search_entity.go`（`ENTITY_SEARCH` 阶段）

触发点：`search_parallel.go`的`PluginSearchParallel.OnEvent`在`CHUNK_SEARCH_PARALLEL` 阶段，**并发**跑两个任务：

- `chunk_search`（向量+关键词混合检索）；
- `entity_search`（图谱查询，仅当 `chatManage.Entity` 非空）。

`PluginSearchEntity.OnEvent` 流程：

1. 无实体 → 跳过；
2. 并发 `graphRepo.SearchNode(NameSpace{KB/Knowledge}, entities)` 查 Neo4j；
3. 合并节点/关系到 `chatManage.GraphResult`；
4. `filterSeenChunk`：从图谱节点的 `chunks` 里，**筛掉已在向量/关键词检索结果中出现过的 chunk**（避免重复）；
5. 剩下的新 chunk → `chunk2SearchResult`转成`SearchResult`（`Score = 1.0`，`MatchType = MatchTypeGraph`）；
6. 富化图片信息、去重，**并入 `chatManage.SearchResult`**。

### 6.3 Neo4j 查询（SearchNode）

```cypher
MATCH (n:LABEL)-[r]-(m:LABEL)
WHERE ANY(nodeText IN $nodes WHERE n.name CONTAINS nodeText)
RETURN n, r, m
```

- **一跳邻域**：查与实体名匹配的节点及其直接邻居、关系；
- `CONTAINS`：实体名的**包含匹配**（比精确匹配更宽松，能命中「实体名」是「问题词」一部分的情况）；
- 返回的节点带 `chunks` 属性 → 反查 chunk 正文。

### 6.4 与混合检索的关系

图谱检索是**第三条召回通道**，与向量、关键词并行，最终都汇入 `SearchResult`，统一走重排序（rerank → MMR）→ 合并 → LLM 生成。所以图谱召回的结果，也会经过重排模型的精排。

```text
QUERY_UNDERSTAND ── 抽实体（Entity）
CHUNK_SEARCH_PARALLEL
   ├─ chunk_search（向量 + 关键词）
   └─ entity_search（Neo4j 查图谱）  ← 只补召回，与 chunk 检索去重
CHUNK_RERANK → CHUNK_MERGE → ... → LLM 生成
```

### 6.5 跨库检索：fan-out + 合并（非单条跨库查询）

图谱检索**不是一条跨库 Cypher 查询**，而是**对每个 KB（或每个文档）并发查一次 `SearchNode`，再合并结果**：

1. `PluginExtractEntity` 已算出 `EntityKBIDs`（开启 ExtractConfig 的 KB）和 `EntityKnowledge`（指定的文档 → KB 映射）；
2. `PluginSearchEntity.OnEvent` 并发 fan-out：
   - 有 `EntityKnowledge`（指定文档）→ 对每个文档调 `SearchNode(NameSpace{KB, Knowledge}, entities)`，label = `ENTITY<KB_ID>:ENTITY<Knowledge_ID>`（**文档级**查询）；
   - 否则 → 对每个 KB 调 `SearchNode(NameSpace{KnowledgeBase: kbID}, entities)`，label = `ENTITY<KB_ID>`（**KB 级**查询）；
3. 合并所有返回的 nodes/relations 到 `chatManage.GraphResult`；
4. `filterSeenChunk` 跨库去重（筛掉已被向量/关键词召回过的 chunk）→ 并入 `SearchResult`。

Agent 侧（`query_knowledge_graph.go`）同理：循环 `knowledge_base_ids`（≤10 个），每个 KB 调 `HybridSearch`（内部走 entity_search），跨 KB 结果去重排序。

## 7. Agent 中的图谱查询工具

文件：`internal/agent/tools/query_knowledge_graph.go`

Agent 模式下，LLM 可主动调用 `query_knowledge_graph` 工具探索实体关系。

`Execute` 流程：

1. 校验 `knowledge_base_ids`（1~10 个）非空；
2. 逐个 KB 检查 `ExtractConfig` 是否配置（Nodes/Relations 非空），未配置的 KB 报错提示；
3. 对每个 KB 调 `HybridSearch`（内部会走 §6 的 entity_search 图谱路径）；
4. 跨 KB 结果去重 + 按分数排序；
5. 输出带图谱配置状态、来源文档、分块内容、相关度的结构化结果（含 `graph_data` 供前端可视化）。

> 工具的 description 里明确写了适用/不适用场景，引导 LLM 在「实体关系探索」时用本工具、在「通用文本检索」时用 `knowledge_search`——和检索工具一样遵循「工具能力边界清晰化」的设计。

### 10.1 生成（文档入库）

```text
文档入库 → 分块
  └─ 每 chunk 入队 TypeChunkExtract（QueueGraph, MaxRetry 3）
       └─ ChunkExtractService.Handle
            ├─ 校验 attempt / knowledge 状态（幂等/取消）

            │      └─ Formater.ParseGraph（fence 剥离 + JSON-like 兜底 + rebuildGraph 去重）
            ├─ node.Chunks = [chunk.ID]
            └─ Neo4jRepository.AddGraph ── apoc.merge.node / merge.relationship ──► Neo4j
```

### 10.2 使用（对话检索）

```text
用户 query
  └─ QUERY_UNDERSTAND
       └─ PluginExtractEntity：Extractor.Extract(query) → chatManage.Entity
  └─ CHUNK_SEARCH_PARALLEL（search_parallel 并行）

       └─ entity_search：PluginSearchEntity
            └─ Neo4jRepository.SearchNode ── MATCH (n)-[r]-(m) WHERE n.name CONTAINS ... ──► GraphData

```
