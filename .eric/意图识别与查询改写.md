# WeKnora 意图识别与查询改写

> 本文梳理 WeKnora 在检索前如何**识别用户意图**和**改写查询**——这是「查询理解（QUERY_UNDERSTAND）」阶段的核心，直接影响后续是否检索、用什么 query 检索。
>
> 核心机制：意图识别和查询改写**不是两个步骤，而是同一个低温度 LLM 调用**，一次性输出结构化 JSON。
>
> 代码基准：`internal/application/service/chat_pipeline/query_understand.go`（插件）+ `config/prompt_templates/rewrite.yaml`（提示词）。

## 1. 总览：一个 LLM 调用做三件事

`PluginQueryUnderstand.OnEvent`（`QUERY_UNDERSTAND` 阶段）用改写模型一次调用，输出结构化 JSON：

```json
{"rewrite_query": "改后的查询", "intent": "kb_search", "image_description": "图片描述（可选）"}
```

三个字段对应三个任务（来自 `rewrite.yaml` 的 `default_rewrite` 模板）：

| 字段 | 任务 | 用途 |
| --- | --- | --- |
| `rewrite_query` | 查询改写 | 后续检索/重排真正使用的 query |
| `intent` | 意图分类 | 决定是否走检索、走哪条路径 |
| `image_description` | 图片分析（有图时） | 多模态：图片的视觉描述 + OCR 文本 |

调用参数：`temperature 0.3`（低温度保证结构化稳定）、`maxTokens 150`（有图 500）、`thinking=false`。

## 2. 触发时机与模型选择

### 2.1 触发与跳过

`OnEvent` 流程开头：

```go
chatManage.RewriteQuery = chatManage.Query   // 先初始化为原 query
hasImages := len(chatManage.Images) > 0
needRewrite := chatManage.EnableRewrite
if !needRewrite && !hasImages {
    return next()   // 未开改写且无图片 → 跳过，直接用原 query
}
```

- `EnableRewrite`（config.yaml `enable_rewrite: true`）开关；
- **即使关闭改写，只要有图片**仍会走这个阶段（因为要做图片分析 `image_description`）。

### 2.2 模型选择（selectModel）

| 场景 | 模型 |
| --- | --- |
| 有图片 | 优先视觉模型（`ChatModelSupportsVision` 的 chat model，或 `VLMModelID`） |
| 纯文本 | `QueryUnderstandModelID`（专门的改写模型）→ 回退 `ChatModelID` |

> 专门的 `QueryUnderstandModelID` 可以让「改写/意图分类」用一个轻量/便宜的模型，与「答案生成」的 chat model 解耦。

## 3. 意图识别：9 类 + 决策优先级

意图类型定义在 `internal/types/chat_manage.go:86`：

```go
IntentKBSearch      = "kb_search"      // 知识库检索
IntentWebSearch     = "web_search"     // 网页搜索
IntentGreeting      = "greeting"       // 问候
IntentChitchat      = "chitchat"       // 闲聊
IntentFollowUp      = "follow_up"      // 追问
IntentImageOnly     = "image_only"     // 纯图片
IntentDocOnly       = "doc_only"       // 纯附件文档
IntentSummarize     = "summarize"      // 总结对话本身
IntentClarification = "clarification"  // 澄清
```

`rewrite.yaml` 里明确写了**从上到下、命中即停**的优先级决策：

| 优先级 | 意图 | 判断 |
| --- | --- | --- |
| 1 | `greeting` | 纯问候/感谢/道别，无实质问题 |
| 2 | `summarize` | 总结**对话本身**（提到「知识库/文档」则归 kb_search） |
| 3 | `web_search` | 明确要实时/最新/外部信息 |
| 4 | `kb_search` | 搜索/查询/整理/列出/提取 KB（含泛读） |
| 5 | `clarification` | 模糊、需检索才能答好 |
| 6 | `follow_up` | 指代上文、无需新检索 |
| 7 | `image_only` | 只分析附件图片本身 |
| 8 | `doc_only` | 只分析附件文档本身 |
| 9 | `chitchat` | 闲聊、无需检索 |

**默认兜底：不确定时一律选 `kb_search`**（宁多检索不漏）。

### 三组易混淆的区分（模板用大量 few-shot 强调）

1. **`image_only`/`doc_only` vs `kb_search`+附件**：上传图问「这是什么」→ `image_only`；问「知识库有类似的吗」→ `kb_search`。
2. **`follow_up` vs `kb_search`**：「上面第二点展开」→ `follow_up`；「这个话题还有什么相关内容」→ `kb_search`。
3. **`summarize` vs `kb_search`**：「总结我们的对话」→ `summarize`；「整理知识库中的数据」→ `kb_search`。

## 4. 查询改写：指代消解 + 省略补全 + 保留检索词

`rewrite.yaml` 的 Task 1 规则：

- **指代消解（coreference resolution）**：把「它/这个/他们/them」等代词替换为明确主语；
- **省略补全（ellipsis completion）**：补全省略的主语/宾语，保证语义完整；
- **保持原意**：结果仍是问句、≤30 词、用 `{{language}}`；
- **关键约束（检索专用）**：改写结果是给检索用的，**必须保留具体实体/关键词/核心搜索词**，禁止生成「请在知识库中查找…」这类元指令。

**正反例**（来自模板 few-shot）：

```text
Input: "再帮我查查他的信息"（上文讨论张三）
✅ 正确: {"rewrite_query":"张三的详细信息是什么", ...}
❌ 错误: {"rewrite_query":"请重新在知识库中查找关于张三的更多信息", ...}
        （错误：含"在知识库中查找"元指令，而非真实搜索词）
```

**例外**：当用户想「泛读/整理/导出」KB 内容（如「整理知识库中的数据，输出体检指标」）时，没有具体检索词可提取，此时**保留原 query 的关键描述词**——`"体检指标数据整理"`，而不是剥离成「数据」。

## 5. 意图驱动后续流水线

`types/chat_manage.go` 的 `NeedsRetrieval()` 决定是否走检索：

```go
func (i QueryIntent) NeedsKBRetrieval() bool {
    switch i {
    case IntentKBSearch, IntentClarification, IntentSummarize, "": // 空=兜底检索
        return true
    default:
        return false
    }
}

func (c *ChatManage) NeedsRetrieval() bool {
    if c.Intent == IntentWebSearch { return c.WebSearchEnabled }
    return c.Intent.NeedsKBRetrieval()
}
```

| 意图 | 是否走检索 |
| --- | --- |
| `kb_search` / `clarification` / `summarize` / 空 | ✅ 走 KB 检索 |
| `web_search`（`WebSearchEnabled` 开启时） | ✅ 走网页检索 |
| `greeting` / `chitchat` / `follow_up` / `image_only` / `doc_only` | ❌ 跳过检索，直接纯 chat |

改写后的 `RewriteQuery` 是后续 `CHUNK_SEARCH`（检索）、`CHUNK_RERANK`（重排）真正使用的 query。

## 6. 意图特定的 system prompt 覆盖

`applyIntentPromptOverride`（`query_understand.go:485`）：当意图**不需要检索**时，把默认 RAG system prompt 换成意图专用 prompt。

- 模板在 `config/prompt_templates/intent_prompts.yaml`，每个模板 `id` 对应一个 `QueryIntent`（如 `greeting`/`chitchat`/`follow_up`/`image_only`）；
- 优先级：**agent 级 `IntentPromptOverrides` > 全局 `IntentSystemPrompts`**。

例：`greeting` 意图用专门的问候 prompt（"The user is greeting you... Respond warmly and naturally"），而不是「根据知识库上下文回答」的 RAG prompt。

## 7. 记忆背景注入 + 解析兜底

### 7.1 长期记忆背景（memoryBackground）

`query_understand.go:335`，把「提问者是谁、长期关注什么」作为 `<asker_background>` 注入改写 prompt：

```text
<asker_background note="背景仅用于消解指代和补全检索词，不要当作问题的一部分">
长期关注：医学影像
常查资料：...
</asker_background>
```

这是**检索前**的记忆应用——让改写「站在提问者视角」消解指代。例如做医学影像的人和做自动驾驶的人问「如何调分割」，会得到不同的改写（检索词不同）。这与「记忆召回（MEMORY_RECALL）」阶段是两回事：这里用的是「全量背景」，只是给改写器看的，不算本轮「用到的记忆」。

### 7.2 结构化输出解析（parseOutput）

`parseStructuredQueryOutput` 优先解析 JSON，失败时找最外层 `{...}` 提取；**解析彻底失败则保留原 query + 空意图**（空意图走 `NeedsKBRetrieval` 的兜底检索）。

## 附：一次查询理解的时间线

```text
用户提问（可能含图片/附件）
  └─ PluginQueryUnderstand.OnEvent
       ├─ EnableRewrite 或 hasImages？否则跳过
       ├─ selectModel（有图选视觉模型，否则 QueryUnderstandModelID）
       ├─ buildPrompts（system=rewrite 模板 + user=问题+图片/附件标记+记忆背景）
       ├─ LLM 调用（temperature 0.3）→ JSON {rewrite_query, intent, image_description}
       ├─ parseOutput（解析 + 兜底）
       ├─ 记忆背景已注入（检索前）
       └─ 非检索意图 → applyIntentPromptOverride（套意图专用 system prompt）
  ↓
后续：intent 决定是否走 CHUNK_SEARCH / CHUNK_RERANK；RewriteQuery 作为检索 query
```
