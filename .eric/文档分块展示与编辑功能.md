# WeKnora 文档分块的展示与编辑功能

> 本文梳理 WeKnora 中「文档分块（chunk）」的**展示、编辑、修订历史、回滚**功能的技术原理、设计与使用。
>
> 核心能力：分块列表展示 → 分块正文编辑 → 修订历史（快照）→ 回滚到任意历史版本，且编辑后自动**重建父块 + 重索引向量**。
>
> 代码基准：`internal/handler/chunk.go`（HTTP 入口）+ `internal/application/service/chunk.go`（核心逻辑）+ `internal/application/repository/chunk.go`（存储）。

## 1. 总览：四大能力

| 能力 | 入口（handler） | 服务方法 | 说明 |
| --- | --- | --- | --- |
| **展示** | `ListKnowledgeChunks` / `GetChunkByIDOnly` | `ListPagedChunksByKnowledgeID` | 分页列出某文档的分块 |
| **编辑** | `UpdateChunk` | `UpdateDocumentChunk` | 编辑分块正文 / 启停用 |
| **修订历史** | `ListChunkRevisions` | `ListChunkRevisions` | 查看历史版本快照 |
| **回滚** | `RevertChunk` | `RevertDocumentChunk` | 回滚到某历史版本 |

**核心设计思想**：*"chunk editing with revision history lets retrieval chunks be edited, diffed and reverted like documents"* —— 把分块当成「可编辑、可 diff、可回滚」的文档一样管理。

三条主线：
- **版本号 + 乐观锁**：`ContentRevision` 自增 + `ExpectedRevision` 校验，防并发覆盖；
- **内容快照**：每次编辑保存旧内容到 `ChunkRevision` 表，支持回滚；
- **编辑即重索引**：编辑正文后，删旧向量 → 重新 embedding → 写回向量库（`IndexStatus` 状态机保证 UI 状态一致）。

## 2. 展示：分块列表与详情

### 2.1 分页列表（ListKnowledgeChunks）

`handler/chunk.go:99`，按 `knowledge_id` 分页列出分块：

- 分页参数：`page`（默认 1）、`page_size`（默认 10，上限 100）；
- **默认只返回 `text` 分块**，可通过 `?chunk_type=image_caption` 等参数覆盖，返回其它类型（图片 OCR、摘要、FAQ 等）；
- 返回 `{data, total, page, page_size}`。

### 2.2 单个详情（GetChunkByIDOnly）

`handler/chunk.go:53`，按 `chunk_id` 返回单个分块（含 `Content`、`ContentRevision`、`IndexStatus`、`ParentChunkID`、前后块关系 `PreChunkID`/`NextChunkID` 等）。

| 字段 | 含义 |

## 3. 编辑：UpdateDocumentChunk 核心逻辑

`service/chunk.go:382`，编辑分块的核心方法。完整流程：

1. **类型校验**：只允许编辑 `ChunkTypeText`（`if chunk.ChunkType != types.ChunkTypeText` → 报错「only text chunks can be edited」）。图片 OCR、摘要、FAQ 等派生分块不可直接编辑。
2. **乐观锁校验**：`expectedRevision != nil && *expectedRevision != chunk.ContentRevision` → 返回 `ErrChunkRevisionConflict`（见 §4）。
3. **内容校验**：
   - 正文 trim 后不能为空；
   - 长度不能超过 `maxEditableChunkLength = 200000` 字节；
   - `validateEditedChunkImages`：编辑后的内容**不能引入新图片**（只允许保留原 `SourceContent` 里出现过的图片 URL）。
4. **保存修订快照**：构造 `ChunkRevision`（记录旧 `Content`/`IsEnabled`/`EditorID`/`EditSource="user"`/`EditedAt`），调 `SaveChunkRevision` 持久化，然后 `ContentRevision++`、更新 `LastEditorID`、`IndexStatus = "processing"`。
5. **联动处理**（见 §6）：
   - 正文变化且是子块 → `rebuildParentContent` 重建父块；
   - 正文/启停变化 → `syncEditedChunkImages` 同步图片子块、`enqueueSummaryRefresh` 刷新摘要；
   - `syncChunkIndex` 重索引向量。
6. **状态收尾**：索引成功 → `IndexStatus = "ready"`；失败 → `IndexStatus = "failed"`（正文仍保存，UI 不显示假成功）。

> 关键：`IndexStatus = "processing"` → `"ready"`/`"failed"` 状态机，保证「编辑保存」和「向量重索引」的状态对 UI 可见、可重试。

## 4. 乐观锁：ExpectedRevision + ContentRevision

**原理**：用「版本号」做乐观并发控制（类似 HTTP `ETag`/`If-Match`），防止两个用户同时编辑同一分块时互相覆盖。

**请求**（`UpdateChunkRequest`）带 `expected_revision`：

```go
type UpdateChunkRequest struct {
    Content          *string `json:"content"`
    IsEnabled        *bool   `json:"is_enabled"`
    ExpectedRevision *int    `json:"expected_revision"`  // 乐观锁：客户端持有的版本号
}
```

**服务端校验**（`UpdateDocumentChunk`）：

```go
if expectedRevision != nil && *expectedRevision != chunk.ContentRevision {
    return nil, ErrChunkRevisionConflict  // 版本不匹配 → 冲突
}
```

**存储层 CAS**（`SaveChunkRevision`）：

```sql
UPDATE chunks SET content = ?, content_revision = ? ...
WHERE id = ? AND tenant_id = ? AND content_revision = ?  -- 用旧版本号做条件更新
```

- 如果 `content_revision` 已变（别人抢先编辑了），`WHERE` 不命中 → 返回 `ErrChunkRevisionConflict`；
- 前端拿到冲突错误后，重新拉取最新分块，让用户基于最新版本再编辑。

> 这就是「分块编辑」比普通文本编辑更严谨的地方：多用户协作下，编辑必须显式声明「基于哪个版本」，避免静默覆盖。

## 5. 修订历史与回滚

### 5.1 修订快照（ChunkRevision）

`types/chunk.go:182`，每次编辑/回滚都会写入一条修订记录：

```go
type ChunkRevision struct {
    ChunkID    string    // 所属分块
    Revision   int       // 修订号（= 编辑前的 ContentRevision）
    Content    string    // 内容快照
    IsEnabled  bool      // 启停状态快照
    EditorID   string    // 编辑者
    EditSource string    // 编辑来源（"user" / 系统）
    EditedAt   time.Time // 编辑时间
}
```

唯一索引 `(ChunkID, Revision)`——每个分块的每个版本号对应一条快照。

### 5.2 查看历史（ListChunkRevisions）

`service/chunk.go:561` → `repository.ListChunkRevisions`，按 `revision DESC` 倒序返回某分块的全部历史版本（前端据此做 diff 展示）。

### 5.3 回滚（RevertDocumentChunk）

`service/chunk.go:565`，回滚本质是「**取历史版本内容 → 再走一遍编辑流程**」：

```go
item, _ := s.chunkRepository.GetChunkRevision(ctx, tenantID, chunkID, revision)
content := item.Content
enabled := item.IsEnabled
return s.UpdateDocumentChunk(ctx, chunkID, &content, &enabled, expectedRevision)
```

- 取目标修订号的内容/启停状态；
- 调 `UpdateDocumentChunk`（同样带 `expected_revision` 乐观锁校验）——所以回滚也会**产生一条新的修订记录 + 触发重索引**，而不是直接覆盖历史。

## 6. 编辑后的联动：重建父块 + 重索引

这是「分块编辑」最有特色的设计——编辑一个子块，会级联触发以下联动：

### 6.1 重建父块（rebuildParentContent）

`service/chunk.go:580`，父-子分块模式下，**编辑子块后要把编辑同步回父块**：

- 父块的 `SourceContent` 是「不可变源基准」（首次编辑前的原始正文）；
- 遍历所有「被编辑过」的子块（`ContentRevision > 0`），把它们的编辑内容按 `StartAt/EndAt` 偏移**逆序覆盖**回父块基准；
- **逆序替换**保证坐标系统不被长度变化破坏；
- 冲突的编辑（区间重叠）→ 保留最新编辑 + 把冲突正文用 `\n\n` 追加，避免静默丢失已接受的编辑。

### 6.2 重索引向量（syncChunkIndex）

`service/chunk.go:644`，编辑后同步向量库：

1. 删旧向量：`DeleteByChunkIDList([chunk.ID])`；
2. 若 `IsEnabled=false` → 直接返回（禁用分块不索引）；
3. 重新 embedding：`buildKnowledgeIndexContent(knowledge, chunk.EmbeddingContent())`（标题 + 面包屑 + 新正文）；
4. **同时重索引生成问题**：把 `GeneratedQuestions` 的每个 question 也作为 IndexInfo 写入（生成问题参与向量匹配）；
5. 写回向量库。

### 6.3 其它联动

| 联动 | 触发条件 | 作用 |
| --- | --- | --- |
| `syncEditedChunkImages` | 正文/启停变化 | 同步图片 OCR/Caption 子块 |
| `enqueueSummaryRefresh` | 正文/启停变化 | 重新入队文档摘要生成 |
| `rebuildParentContent` | 正文变化且是子块 | 重建父块正文 |

## 附：一次编辑的完整时序

```text
前端编辑分块正文（带 expected_revision）
  └─ PUT /chunks/:id → UpdateChunk handler
       └─ UpdateDocumentChunk
            ├─ 类型校验（只允许 text chunk）
            ├─ 乐观锁校验（expected_revision == ContentRevision？）
            ├─ 内容校验（非空 / ≤200000 字节 / 不引入新图片）
            ├─ 保存修订快照（ChunkRevision）+ ContentRevision++
            ├─ 联动：rebuildParentContent（重建父块）
            ├─ 联动：syncEditedChunkImages（同步图片子块）
            ├─ 联动：enqueueSummaryRefresh（刷新摘要）
            └─ syncChunkIndex（删旧向量 → 重新 embedding → 写回）
                 └─ IndexStatus: processing → ready / failed
```
