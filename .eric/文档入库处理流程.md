# WeKnora 文档入库处理全流程

> 本文梳理 WeKnora 从「上传文档」到「处理完成」的端到端流水线，逐环节说明核心处理逻辑。
>
> 核心链路：**上传 → 入队处理任务 → 文档解析（docreader）→ 图片/音频处理 → 分块 → 建索引 → 后处理（异步富化）→ 完成**。
>
> 代码基准：`internal/`（Go 后端）+ `docreader/`（Python 文档解析 gRPC 服务）。

## 1. 总体架构与状态机

### 1.1 状态机（ParseStatus）

`internal/types/knowledge.go:42`：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已创建，等待处理 |
| `processing` | 正在解析（docreader / 分块 / 建索引） |
| `finalizing` | 主解析完成，富化子任务（摘要/问题/图谱）仍在跑；**此时已可向量检索** |
| `completed` | 全部子任务完成 |
| `failed` | 处理失败 |
| `cancelled` | 用户取消（保留已写入的 chunk/index，可重新解析） |
| `deleting` | 删除中（防异步任务冲突） |

**关键设计**：`finalizing` 状态 + `pending_subtasks_count` 计数器。主流程建完索引后就进入 `finalizing`，富化子任务各自完成后**原子递减**计数器，最后一个归零的原子地把状态提升为 `completed`。

### 1.2 任务队列（Asynq）

`internal/types/task.go`：

| 队列 | 用途 |
| --- | --- |
| `postprocess` | 统一后处理调度 |
| `summary` | 摘要生成 |
| `question` | 问题生成 |
| `graph` | 知识图谱抽取 |
| `multimodal` | 图片 OCR + VLM Caption |
| `wiki` | Wiki 页面同步 |

关键任务类型：

```go
TypeDocumentProcess     = "document:process"      // 文档处理主任务
TypeKnowledgePostProcess = "knowledge:post_process" // 统一后处理调度
TypeQuestionGeneration  = "question:generation"    // 问题生成
TypeSummaryGeneration   = "summary:generation"     // 摘要生成
TypeDataTableSummary    = "datatable:summary"      // 表格摘要
TypeImageMultimodal     = "image:multimodal"       // 图片多模态
TypeChunkExtract        = "chunk:extract"          // 图谱抽取
```

## 2. 上传入口

文件：`internal/handler/knowledge.go:316`（`CreateKnowledgeFromFile`）

1. HTTP 接收文件（multipart），校验知识库访问权限；
2. 调 `kgService.CreateKnowledgeFromFile`：
   - 保存文件到对象存储（`fileService.SaveFile`）；
   - 创建 `Knowledge` 记录（`ParseStatus = pending`）；
   - **入队 `TypeDocumentProcess` 任务**（携带 `KnowledgeID` / `FilePath` / `FileType` / `EnableMultimodel` / `EnableQuestionGeneration` 等 payload）；
3. 立即返回（异步处理）。

> 其他入口：`CreateKnowledgeFromURL`（URL 导入）、`CreateManualKnowledge`（手工 Markdown）、`CreateKnowledgeFromPassage`（纯文本）。它们都入队同一个 `TypeDocumentProcess` 任务，区别只在 payload（`FilePath` / `URL` / `Passages`）。

## 3. 处理任务 ProcessDocument

文件：`internal/application/service/knowledge_process.go:3160`

`ProcessDocument` 是主任务处理器，核心步骤：

### 3.1 前置守卫

- 幂等：`deleting` / `cancelled` / `completed` 直接返回；`failed` 允许重试；
- 获取 KB + 解析处理配置（`ResolveProcessConfig(kb, processOverrides)`）；
- 标记 `processing`（`markKnowledgeProcessing`，清空 error_message）；
- 能力校验：
  - 图片文件需 `EnableMultimodel`；
  - 音频文件需 ASR 模型；
  - 视频文件不支持。

### 3.2 按来源分派（四种来源）

```text
file_url  → SSRF 校验 → 下载 → 存文件 → convert
url       → convert（网页抓取 → Markdown）
passages  → 直接分块（纯文本，无解析）
file      → convert（文件 → Markdown）
```

### 3.3 音频转写（ASR）

若 `convertResult.IsAudio`：调 ASR 模型 `Transcribe`，把音频转成文本，替换 Markdown 内容。

### 3.4 图片存储

`imageResolver.ResolveAndStore`（内联 base64 / 图片字节）+ `ResolveRemoteImages`（http/https 远程图片）→ 下载并上传到对象存储，替换 Markdown 里的图片引用。

### 3.5 分块（见 §5）

```go
if eff.ChunkingConfig.EnableParentChild {
    parentCfg, childCfg := buildParentChildConfigs(...)
    pcResult := chunker.SplitParentChild(content, parentCfg, childCfg)  // 父-子分块
} else {
    splitChunks := chunker.Split(content, chunkCfg)  // 单层分块
}
```

### 3.6 建索引（见 §6）

`processChunks(ctx, kb, knowledge, chunks, processOpts)`。

## 4. 文档解析 convert（docreader）

文件：`internal/application/service/knowledge_process.go:3576`（`convert`）+ `docreader/`（Python 服务）

`convert` 调用 `resolveDocReader` 解析出 docreader 引擎，再 `callDocReaderWithTimeout` 调 gRPC：

- **docreader 是独立的 Python gRPC 服务**（`docreader/main.py` 的 `DocReaderServicer`）；
- 支持多种格式：docx / doc / pdf / pptx / xlsx / epub / html / mhtml / markdown / txt 等；
- 输出统一的 `ReadResult`：`MarkdownContent`（正文）、`Images`（图片 + Caption + OCR）、`Metadata`（标题等）。

**引擎路由**（`resolveDocReader` + `ParserEngineRules`）：根据文件类型选解析引擎（内置 builtin / anydoc / MinerU / Weaviate Cloud 等）。

> 解析失败按重试策略处理：临时错误（超时、限流）→ Asynq 重试；不可恢复错误 → 标记 `failed`。

## 5. 分块 chunker

文件：`internal/infrastructure/chunker/`

分块配置来自 `ChunkingConfig`（`chunk_size=512` / `chunk_overlap=50` / `split_markers` / `strategy` / 父-子分块参数）。

- **单层分块** `chunker.Split`：按 `strategy` 选层级（`legacy`/`auto`/`heading`/`heuristic`/`recursive`），详见《检索质量深度剖析.md》§2；
- **父-子分块** `chunker.SplitParentChild`：父块（`ParentChunkSize`）+ 子块（`ChildChunkSize`），子块用于向量匹配、父块用于上下文；
- 分块结果带 `ContextHeader`（标题面包屑）和 `Start/End`（源文件偏移）。

## 6. 建索引 processChunks

文件：`internal/application/service/knowledge_process.go:244`

### 6.1 幂等清理

先删除旧数据（重解析时避免重复）：

1. 删旧 chunks（`DeleteChunksByKnowledgeID`）；
2. 删旧向量索引（`DeleteByKnowledgeIDList`）；
3. 删旧知识图谱（`graphEngine.DelGraph`）。

### 6.2 创建 chunk 对象

- **父块**（父-子模式）：`ChunkType = parent_text`，建 prev/next 链接；
- **文本块**：`ChunkType = text`，绑定 `ParentChunkID`；
- **图片子块**：每个图片的 OCR 和 Caption 各生成一个 chunk（`image_ocr` / `image_caption`）；
- 文本块之间建 prev/next 链接（非父-子模式）。

### 6.3 存 DB

`chunkService.CreateChunks` —— **总是执行**，即使不建向量索引（wiki / 图谱 / 摘要也需要 chunk）。

### 6.4 建向量/关键词索引

只对 **text 子块**（父块不索引，用于上下文展开）：

```go
indexContent := buildKnowledgeIndexContent(knowledge, chunk.EmbeddingContent())
```

**embedding 输入 = 文档标题 + ContextHeader（标题面包屑）+ chunk 正文**。标题和面包屑前置是为了提升「问句 query」与「陈述式 chunk」之间的语义对齐（检索质量细节）。

`retrieveEngine.BatchIndex` → 向量 + 关键词混合索引（见《检索质量深度剖析.md》§3）。

### 6.5 存储配额与完成

- 估算存储占用，检查租户配额（超限 → `failed`）；
- `finalizeIndexedKnowledgeState`：有文本块或待处理多模态 → `processing`（等待后处理）；否则直接 `completed`；
- 入队多模态任务（图片）或 `TypeKnowledgePostProcess` 后处理任务；
- 更新租户存储用量。

## 7. 后处理（异步富化）

文件：`internal/application/service/knowledge_post_process.go`（`KnowledgePostProcessService.Handle`）

主流程建完索引后，后处理统一调度富化子任务：

### 7.1 计算子任务数

```go
willSpawnSummary  := len(textChunks) > 0                                 // 摘要
willSpawnQuestion := willSpawnSummary && kb.NeedsEmbeddingModel() &&
                     eff.QuestionGenerationConfig.Enabled                  // 问题生成
willSpawnWiki     := kb.IndexingStrategy.WikiEnabled && len(textChunks) > 0 // Wiki
willSpawnAutoTag  := ...                                                   // 自动打标签
graphChunkCount   := eff.GraphEnabled ? len(textChunks) : 0               // 图谱（每 chunk）
```

- 摘要：1 个子任务；
- 问题生成：按 `questionGenChunkBatchSize` 分批（每批 1 个子任务）；
- Wiki：1 个子任务；
- 图谱：每 chunk 1 个子任务。

### 7.2 状态切换

- **无子任务** → 直接 `completed`（快路径）；
- **有子任务** → 先原子地翻到 `finalizing` + 写入 `pending_subtasks_count`，再 fan-out 各子任务。

### 7.3 各富化子任务

| 子任务 | 任务类型 | 逻辑 |
| --- | --- | --- |
| 摘要生成 | `summary:generation` | LLM 总结文档 → 写入 knowledge.description |
| 问题生成 | `question:generation` | 每 chunk 预生成问题（HyDE 式）→ 写 chunk metadata |
| 知识图谱 | `chunk:extract` | LLM 抽实体+关系 → 写 Neo4j（见《知识图谱生成与使用逻辑.md》） |
| Wiki 同步 | `wiki:ingest` | 文档蒸馏成 Wiki 页面 |
| 自动打标签 | `knowledge:auto_tag` | 文档自动关联知识库已有标签 |
| 多模态 | `image:multimodal` | 图片 OCR + VLM Caption（在主流程中入队，不在后处理） |

### 7.4 完成

每个子任务完成后 `FinalizeSubtask` **原子递减** `pending_subtasks_count`，归零时自动把 `parse_status` 提升为 `completed`。

## 8. 关键数据结构

| 类型 | 文件 | 说明 |
| --- | --- | --- |
| `Knowledge` | `types/knowledge.go` | 知识实体：`ParseStatus` / `PendingSubtasksCount` / `FilePath` / `FileType` 等 |

| `ProcessConfig`（`ResolveProcessConfig`） | `knowledge_process_config.go` | 合并 KB 默认 + 单文档覆盖后的有效处理配置 |

## 9. 附：完整时序图

```text
上传文档（CreateKnowledgeFromFile）
  ├─ 存文件 → 创建 Knowledge(pending)
  └─ 入队 document:process
       └─ ProcessDocument
            ├─ 守卫（幂等/取消）+ 标记 processing
            ├─ 按来源：file/url/file_url/passages
            │    └─ convert() → docreader gRPC 解析 → Markdown
            ├─ ASR 转写（音频）
            ├─ 图片存储（ResolveAndStore / ResolveRemoteImages）
            ├─ 分块（chunker.Split / SplitParentChild）
            └─ processChunks
                 ├─ 幂等清理（删旧 chunk/索引/图谱）
                 ├─ 创建 chunk（父块/文本块/图片块）
                 ├─ 存 DB（始终执行）
                 ├─ 建索引（标题+面包屑+正文 → embedding → 向量+关键词）
                 └─ finalize → processing，入队 post_process 或多模态
       └─ KnowledgePostProcessService.Handle
            ├─ 计算富化子任务数（摘要+问题+wiki+图谱）
            ├─ 无子任务 → completed
            └─ 有子任务 → 翻 finalizing + 写 pending_subtasks_count → fan-out
                 ├─ summary:generation（摘要）
                 ├─ question:generation（问题，按批）
                 ├─ chunk:extract（图谱，每 chunk）
                 ├─ wiki:ingest（Wiki）
                 └─ 各自 FinalizeSubtask 递减 → 归零 → completed
```
