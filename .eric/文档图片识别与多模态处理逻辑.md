# WeKnora 文档图片识别与多模态处理逻辑

> 本文梳理 WeKnora 的**文档图片处理**子系统——从各种格式的文档中**提取**图片、**过滤**图标、**落对象存储**，再交给 **VLM（视觉语言模型）做 OCR + 图片描述（caption）**，生成 `image_ocr` / `image_caption` 子 chunk 并接入检索与回答的全过程。
>
> 核心思想：图片的「文字信息」靠 OCR 提取、「视觉语义」靠 VLM 描述，两者都落成**子 chunk**挂在包含该图的文本 chunk 之下，让图片内容也能被语义检索命中、并以文本形式进入 LLM 上下文。
>
> 代码基准：`internal/`（Go 后端）。它属于**文档处理（离线入库）**的一环——关掉 VLM，图片照样入库，但图片里的文字和视觉信息就进不了检索与回答。

## 1. 总览：一条链路，两个「识别」时机

```text
文档/图片文件
   │  ① 引擎选择（按文件类型 → 解析引擎）
   ▼
解析 → Markdown + 图片引用（ImageRefs，内嵌字节）
   │  ② 提取 + 过滤 + 落对象存储（ImageResolver）
   ▼
文本 chunk（Markdown 引用处）…… 图片存进 COS/MinIO/S3/local
   │  ③ 识别：VLM OCR + caption（异步 asynq 任务）
   ▼
子 chunk：image_ocr（OCR 文本） + image_caption（图片描述）
   │  ④ 索引 + 组装进上下文
   ▼
检索/回答时以「Image caption / Image text (OCR)」形式注入
```

关键点：图片的「识别」其实发生在**两个不同时机**——

- **MinerU / PaddleOCR-VL 引擎**：解析阶段就把文字 OCR 出来。它们是文档理解模型，输出的 Markdown 里已含正文文字、表格、公式。
- **builtin / simple / anydoc 引擎**：解析阶段只把图片**抠出来**（原始字节），OCR 和 caption 全部**延迟到异步 VLM 阶段**才做。

但无论哪个引擎，图片最终都会走同一条 VLM 富化流程（第 5 节），所以识别路径是统一的。MinerU/PaddleOCR 的价值在于文档级 OCR 提前进了 Markdown；VLM 阶段对图片裁剪块的 caption + 逐图 OCR 则对所有引擎一视同仁。

**贯穿全文的核心类型**（`internal/types/chunk.go`）：

```go
// 图片子 chunk 类型
ChunkTypeImageOCR     ChunkType = "image_ocr"      // :21 图片 OCR 文本
ChunkTypeImageCaption ChunkType = "image_caption"  // :23 图片描述

// 与 chunk 关联的图片信息（存 JSON 到 ImageInfo 列）
type ImageInfo struct {        // :86
    URL         string        // 图片 URL（对象存储）
    OriginalURL string        // 原始图片 URL
    StartPos    int           // 图片在文本中的开始位置
    EndPos      int           // 图片在文本中的结束位置
    Caption     string        // 图片描述（VLM 生成）
    OCRText     string        // 图片 OCR 文本（VLM 生成）
}
```

## 2. 引擎选择：哪种格式走哪个解析引擎

引擎在 `internal/infrastructure/docparser/engines.go` 注册，每个声明自己支持的 `FileTypes()`：

| 引擎 | 支持的格式 | 说明 |
| --- | --- | --- |
| `builtin` | docx/doc/pdf/xlsx/epub/html/xmind + 图片 + 音频 | Python DocReader 服务（复杂格式） |
| `simple` | md/txt/csv/json + 图片 + 音频 | Go 原生，无需外部服务 |
| `anydoc` | office 文档（docx/pptx/xlsx/pdf） | 进程内转换，无外部服务 |
| `mineru` / `mineru_cloud` | pdf + 图片 + office | MinerU 自建/云，解析即 OCR |
| `paddleocr_vl` / `paddleocr_vl_cloud` | pdf + 图片 | PaddleOCR-VL，解析即 OCR |
| `weknoracloud` | docx/doc/pdf/xlsx/pptx | 托管服务 |

**引擎选择链路**：

1. `ChunkingConfig.ResolveParserEngine(fileType)`（`internal/types/knowledgebase.go:284`）按 KB 配置的 `ParserEngineRules`（`文件类型 → 引擎` 规则表）匹配；没匹配到返回空（= builtin）。
2. `docparser.NewReader(...)`（`engine_registry.go:69`）实际建 reader：
   - 引擎名本地已注册 → 走对应 reader；
   - 引擎名为空且是「简单格式」→ `SimpleFormatReader`（Go 原生）；
   - 其余 → `remoteReader`（Python docreader 客户端）。

`builtin_converter.go:41` 的 `IsSimpleFormat` 定义「简单格式」= md/txt/csv/json + 图片 + 音频，都由 Go 直接处理、绕过 Python 服务。

**独立图片文件**（用户直接上传 png/jpg）走 `SimpleFormatReader.Read → imageToResult`（`builtin_converter.go:84`）：把整张图包成 `![name](images/name)` 的 Markdown 引用，`IsOriginal: true`。之后和「文档内嵌图片」走完全相同的下游链路。

## 3. 提取：图片在 Markdown 里的多种形态

这是最精细的一块。`internal/infrastructure/docparser/image_resolver.go` 的 `ResolveAndStore`（:80）按顺序处理**七种形态**：

| 形态 | 处理函数 | 说明 |
| --- | --- | --- |
| `[![alt](img)](link)` 嵌套链接图 | `UnwrapLinkedImages`（:644） | 先拍平成 `![alt](img)` |
| `![alt](data:image/*;base64,…)` | `ResolveDataURIImages`（:686） | 解码 base64 → 存 |
| `<img src="data:image/…">` | `ResolveHTMLDataURIImages`（:352） | 同上 |
| 裸 base64（`base64,…` 无 mime 前缀） | `ResolveBareBase64Content`（:463） | 靠魔数嗅探类型 |
| `![alt](images/foo.png)` 相对引用 | `scanMarkdownImageTargets` + `saveReferencedImage`（:128） | 与解析器返回的 `ImageRefs`（内嵌字节）按路径匹配 |
| `<img src="images/foo.png">` 相对 | `ResolveRelativeHTMLImages`（:414） | 同上 |
| `![alt](http(s)://…)` 远程 | `ResolveRemoteImages`（:962） | SSRF 校验 + 下载 + 限流限大小 |

`markdown_image_scanner.go` 是那个**手写的 `![alt](url)` 精确解析器**——处理嵌套括号、`<角括号>`、title 后缀、转义字符，比正则更稳（`:14 scanMarkdownImageTargets`）。

**引擎特化的提取**（都是「服务返回 base64 图片 → Go 解码成 ImageRef」）：

- **MinerU**（`mineru_converter.go:291 processImages`）：`/file_parse` 返回 `path → "data:image/png;base64,…"` 字典，Go 端解码，并做 `normalizeMinerUImagePath`（:460）处理 `./images/` 前缀、URL 转义、中文空格路径。
- **PaddleOCR-VL**（`paddleocr_vl_converter.go:216 processImages`）：`/layout-parsing` 按页返回 markdown + 图片字典，逐页合并，复用同一套 `mineruImageOriginalRefs` 做路径匹配。
- **anydoc**（`anydoc_reader.go:41`）：进程内把 office 文档转 Markdown，`extractImages` 开关控制是否抠图（关掉能省一半解析时间）。

**扫描 PDF 的兜底**（`anydoc_reader.go:84-112`）：anydoc 发现 PDF「无文字层」（`PDFNeedsOCR` / markdown 为空）时，回退到 builtin 让 docreader 把每页栅格化做 OCR，并在 `Metadata` 里写入：

```go
result.Metadata["anydoc_fallback"] = "scanned_pdf"
result.Metadata["image_source_type"] = "scanned_pdf"   // :110
```

这个 `image_source_type` 会一路传到 VLM 阶段，触发不同的 OCR prompt（见第 6 节）。

## 4. 过滤 + 落对象存储

- **图标过滤**（`image_resolver.go:46 isIconImage`）：任一维 < 64px 或 < 512 字节 → 视为图标/装饰元素丢弃。网页里几百个 tracking pixel / spacer gif 就靠它挡掉（`:753` 还专门聚合了「filtered out as icon」这个跳过原因，避免刷屏日志）。
- **存储**（`image_resolver.go:202`）：`fileSvc.SaveBytes` 写入对象存储，返回 `provider://` URL（`local://` / `minio://` / `cos://` / `tos://` / `s3://` / `obs://`）。
- **去重**（`:181`）：同一源图（按 `Filename`）被多个 markdown 引用时复用已存副本，不重复写对象存储。
- **白名单**（`:254 isWhitelistedImageHost`）：`IMAGE_HOST_KEEP_URL` 配置的主机不落库、保留原始 URL，但字节仍下载用于 OCR/caption。

## 5. 识别：VLM 做 OCR + caption

这是子系统核心。分「入队」和「worker」两半。

### 5.1 入队

`internal/application/service/knowledge_process.go:3806 enqueueImageMultimodalTasks`——对每个已存图片：

1. 找到**包含它 URL 的父文本 chunk**（在解析出的 `ParsedChunk` 里按 `strings.Contains(c.Content, img.ServingURL)` 匹配；匹配不到就挂第一个 chunk）。
2. 入队一个 `image:multimodal` asynq 任务（`payload` 见 `internal/types/task.go:497`）：

```go
payload := types.ImageMultimodalPayload{
    TenantID:        knowledge.TenantID,
    KnowledgeID:     knowledge.ID,
    KnowledgeBaseID: kb.ID,
    ChunkID:         chunkID,          // 父文本 chunk
    ImageURL:        img.ServingURL,   // provider:// URL
    EnableOCR:       true,
    EnableCaption:   true,
    Language:        lang,
    ImageSourceType: metadata["image_source_type"], // 可能为 "scanned_pdf"
    Attempt:         attempt,
    ImageIndex:      idx,
}
```

任务参数：`Queue("multimodal")`、`MaxRetry(3)`、`Timeout(30m)`。

### 5.2 worker

`internal/application/service/image_multimodal.go:137 Handle`：

1. **孤儿/取消检查**（`shouldDropOrphanedMultimodal` :372）——知识已被删除/取消就丢弃，避免浪费 VLM 调用。
2. **解析 VLM**（`resolveVLM` :517）——从 KB 配置拿模型（新式 ModelID 走 `ModelService.GetVLMModel`，旧式内联 BaseURL 走 `vlm.NewVLMFromLegacyConfig`）。
3. **读图片字节**（`readImageBytes` :610）——`provider://` 走 FileService（绝不能丢给 HTTP 下载器），`http(s)://` 走 SSRF 安全下载，旧式 `ImageLocalPath` 读本地文件兜底。
4. **OCR**（:260）——按 `ImageSourceType` 选 prompt（见第 6 节），`vlmModel.Predict(ctx, [][]byte{imgBytes}, prompt)`，结果 `sanitizeOCRText` 清洗后写入 `imageInfo.OCRText`。
5. **caption**（:289）——`buildVLMCaptionPrompt`（:53，按 KB 语言生成「用 X 语言简述图片内容」，可追加自定义指令）→ `imageInfo.Caption`。
6. **造子 chunk**（:303-335）：OCR/caption 各自独立成一个 chunk，`ParentChunkID` 指向父文本 chunk，`ImageInfo` 存 JSON。
7. **索引**（`indexChunks` :427）——把子 chunk 的 Content 送进检索引擎（向量 + 关键词），并标记 `ChunkStatusIndexed`。KB 无 embedding 管线（如纯 Wiki KB）则跳过索引但仍持久化。
8. **汇总**（`checkAndFinalizeAllImages` :650）——Redis 计数器 `multimodal:pending:{knowledgeID}` 减到 0 → 触发 `knowledge:post_process`（生成摘要/推荐问题）。

**VLM 后端**（`internal/models/vlm/vlm.go:86 NewVLM`）：

| 后端 | 条件 | 文件 |
| --- | --- | --- |
| Ollama | 本地模型 / `InterfaceType=ollama` | `ollama.go` |
| WeKnoraCloud | provider 检测为 WeKnoraCloud | `weknoracloud.go` |
| RemoteAPI | 其余（OpenAI 兼容） | `remote_api.go` |

三层装饰器：`debugVLM`（日志）→ `wrapVLMLangfuse`（可观测）→ `wrapVLMConcurrency`（按模型限并发，`concurrency_wrapper.go`）。

### 5.3 同步对账路径

`knowledge_process.go:2930-3009` 还有一条**同步**路径（重新处理/更新图片时用）：按 `OriginalURL` 匹配已有 `image_ocr`/`image_caption` 子 chunk，OCR/caption 变了就更新、缺失就新建，比全量重建省 VLM 调用。

## 6. 「不同类型的图片」如何区分

代码里**没有**按图片「语义内容」（截图 / 示意图 / 图表 / 照片）做分类。图片的「类型」按三个正交维度区分：

| 维度 | 取值 | 作用 | 代码位置 |
| --- | --- | --- | --- |
| **文件格式** | png/jpg/gif/bmp/tiff/webp/svg | 魔数嗅探 / 扩展名 → 决定落盘后缀 | `sniffImageMime`、`extFromMime`（image_resolver.go） |
| **嵌入形态** | markdown img / HTML img / data URI / 裸 base64 / 远程 URL / 相对引用 | 决定走哪个 resolver | 第 3 节那张表 |
| **来源上下文** | `scanned_pdf` vs 默认 | 只切换 OCR 的 prompt | `image_multimodal.go:262` |

其中**唯一改变识别行为的**是第三个维度。`image_multimodal.go:28-51` 有两个 OCR prompt：

- **默认** `vlmOCRPrompt`：抽正文文字 → Markdown（表格转 Markdown、公式转 LaTeX、忽略页眉页脚、无文字回 `No text content.`）。
- **扫描 PDF** `vlmOCRScannedPDFPrompt`（`ImageSourceType=="scanned_pdf"` 时用）：额外要求「保留原文档段落/层级结构」，是带版面提取的重型 OCR。

所以结论：**所有图片——不管内容是截图、流程图、表格还是照片——识别动作都是同一套 OCR（抽文字）+ caption（VLM 描述）**，只有「扫描 PDF 页」这类整页图像会换一个更重版面的 OCR prompt。「图表 vs 照片」的语义区分，全部压在 VLM 的 caption 能力上，没有前置分类器。

## 7. 子 chunk 与索引

生成的两个子 chunk（`image_multimodal.go:303-335`）：

| chunk | `Content` | `ChunkType` | `ParentChunkID` |
| --- | --- | --- | --- |
| OCR 块 | OCR 提取的文本 | `image_ocr` | 父文本 chunk |
| caption 块 | VLM 图片描述 | `image_caption` | 父文本 chunk |

两者都设 `IsEnabled=true`、`Flags=ChunkFlagRecommended`（推荐标志），`ImageInfo` 列存 `[{url, original_url, caption, ocr_text}]` 的 JSON。

索引（`indexChunks` :427）把它们送进检索引擎，与普通文本 chunk 同等对待——所以「图片里的文字」和「图片的语义描述」都能被关键词/向量检索命中。这正是图片信息不丢失的关键：原始图片只留下一个 Markdown 占位，但 OCR 文字 + 描述作为独立 chunk 进索引。

## 8. 下游：OCR/caption 进入回答上下文

- `internal/searchutil/imageinfo.go`：检索命中后，把子 chunk 的 caption/OCR 以 `> **Image caption:** …` / `> **Image text (OCR):** …`（:388、:389）或 XML `<image_caption>`/`<image_ocr>`（:434）注入上下文；HTML 场景下处理「OCR 文本本身含 `<img>` 标签」等边界（`imageinfo_html_test.go`）。
- `internal/application/service/chat_pipeline/merge.go`：把 `image_ocr`/`image_caption` 子 chunk 合并进父块上下文（:346、:411）。
- `internal/application/service/knowledgebase_search_results.go:198`：结果里识别/展示图片类 chunk。

## 10. 附：时序图

```text
上传文档/图片
  → knowledgeService.ProcessDocument
       ├─ ResolveParserEngine(fileType) → 选引擎
       ├─ docparser.NewReader → 对应 Reader.Read()
       │     ├─ builtin/simple/anydoc：Markdown + ImageRefs(原始字节)
       │     ├─ mineru/paddleocr：Markdown(含OCR文字) + base64图片 → 解码
       │     └─ anydoc 扫不出文字 → fallback builtin + image_source_type=scanned_pdf
       ├─ ImageResolver.ResolveAndStore(markdown, ImageRefs)
       │     ├─ 依次：嵌套链接图 → data URI → HTML img → 裸base64
       │     │        → 相对引用 → 远程URL
       │     ├─ isIconImage 过滤图标(<64px / <512B)
       │     └─ fileSvc.SaveBytes → provider:// URL
       ├─ 分块 → 文本 chunk（含图片 Markdown 占位）
       └─ enqueueImageMultimodalTasks
             └─ 每张图一个 image:multimodal 任务(EnableOCR+EnableCaption)

asynq worker: ImageMultimodalService.Handle
  ├─ resolveVLM → VLM(Ollama/WeKnoraCloud/RemoteAPI)
  ├─ readImageBytes（provider:// 走 FileService，http 走 SSRF 下载）
  ├─ OCR：vlmOCRPrompt（默认）| vlmOCRScannedPDFPrompt（扫描PDF）
  ├─ caption：buildVLMCaptionPrompt（按语言）
  ├─ 造子 chunk：image_ocr + image_caption（Parent=父文本chunk）
  ├─ indexChunks → 向量+关键词索引
  └─ checkAndFinalizeAllImages → pending 减到 0 → knowledge:post_process

检索/回答
  → 命中 image_ocr/image_caption 子 chunk
  → searchutil/imageinfo 注入 "Image caption / Image text (OCR)"
  → merge.go 合并进父块上下文 → 交给 LLM
```
