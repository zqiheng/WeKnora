# WeKnora 存储方案与检索引擎架构

> 本文梳理 WeKnora 的**检索存储层**——「文本 chunk + 向量 + 关键词」到底存在哪、怎么存、怎么被检索。核心回答三个问题：
>
> 1. **支持哪些存储引擎**（9 种：Postgres / SQLite / Elasticsearch / OpenSearch / Qdrant / Milvus / Weaviate / Doris / Tencent VectorDB）；
> 2. **collection/index 怎么切分**（按嵌入维度，而非按知识库；不同 KB 默认挤在同一个 collection 里，靠 `knowledge_base_id` 字段隔离）；
> 3. **关键词（BM25）存哪里**（不是独立的一套库，而是和向量**存在同一份文档里**——`content` 文本字段 + `embedding` 向量字段）。
>
> 代码基准：`internal/types/vectorstore.go`（数据模型）、`internal/application/service/retriever/`（引擎抽象层）、`internal/application/repository/retriever/*`（各引擎实现）、`internal/container/engine_factory.go`（引擎装配）。
>
> 本文是「基础设施」视角，回答「数据落在哪个物理存储、以什么粒度组织」。检索时的质量机制（混合检索/RRF/重排/父块子块）见《检索质量深度剖析》，多知识库权限见《Tag标签系统设计与使用逻辑》之外的相关讨论。

## 1. 总览：三层结构

检索存储从「业务调用」到「物理磁盘」分三层：

```text
业务 service 层（knowledgebase_search.go 等）
   │  调 Retrieve / Index
   ▼
引擎抽象层（application/service/retriever/）
   ├─ KeywordsVectorHybridRetrieveEngineService   （KVHybrid：单引擎，keyword+vector 合一）
   └─ CompositeRetrieveEngine                     （组合多个 {引擎, 检索类型} 对）
   │  每个引擎 = 一个 RetrieveEngineRepository
   ▼
物理存储层（application/repository/retriever/*/）
   Qdrant collection / ES index / Milvus collection / PG 表 / SQLite 表 / ...
```

一句话：**业务层不知道底层是哪个库**，只面对统一的 `Retrieve`/`Index` 接口；底层每个引擎都同时支持「关键词检索」和「向量检索」，物理上把 chunk 的 `content`（供关键词）和 `embedding`（供向量）写在同一条记录里。

## 2. 范围界定：检索存储 vs 其他存储

WeKnora 的「存储」分几类，本文只讲第一类：

| 类别 | 存什么 | 在哪 |
| --- | --- | --- |
| **检索存储**（本文） | chunk 文本 + 向量 + 关键词索引 | Qdrant / ES / Milvus / PG / ... |
| 元数据库 | 知识库、文档、chunk、tag、会话、消息等业务表 | GORM 主库（Postgres 等） |
| 文件存储 | 原始上传文件（PDF/Word/...） | 本地 / MinIO / COS（`storage_engine_config`） |
| 图数据库 | 实体-关系知识图谱 | Neo4j |
| 检索增强索引 | LLM Wiki / FAQ 等问题 | 依赖检索存储，见各专项文档 |

检索存储的关键特征：它是**可插拔的**（多引擎、多实例），且和元数据库是**两个物理库**——chunk 的元信息（标题、状态、父子关系）在元数据库，chunk 的**可检索物**（content + embedding）在检索存储。

## 3. 引擎清单：9 种 + 两种注册路径

引擎类型常量在 `internal/types/retriever.go:8-27`。能被「注册成 DB 绑定的 VectorStore」的是 7 种（`vectorstore.go:87-95` 的 `validEngineTypes`）：

| 引擎 | 常量值 | 能否作为 DB 绑定 store |
| --- | --- | --- |
| Elasticsearch | `elasticsearch` | ✅（v7/v8 自动识别） |
| OpenSearch | `opensearch` | ✅ |
| Qdrant | `qdrant` | ✅ |
| Milvus | `milvus` | ✅ |
| Weaviate | `weaviate` | ✅ |
| Doris | `doris` | ✅ |
| Tencent VectorDB | `tencent_vectordb` | ✅ |
| Postgres | `postgres` | ❌（只能走 env，绑定默认连接） |
| SQLite | `sqlite` | ❌（只能走 env） |

Postgres / SQLite 被排除在 DB 绑定之外的原因（`vectorstore.go:78-86` 注释）：它们的 embedding 表是**单张硬编码表名**，无 per-store 分区，注册第二个同引擎实例没有隔离效果，所以只保留 `RETRIEVE_DRIVER` 这一条 env 路径。

**两种注册路径**：

```text
路径 A（env 虚拟 store，只读）
  RETRIEVE_DRIVER=qdrant,elasticsearch_v8
    → BuildEnvVectorStores()（vectorstore.go:803）
    → 生成虚拟 VectorStore（ID = "__env_qdrant__" 等，EnvStoreIDPrefix="__env_"）
    → 只读、不落 vector_stores 表

路径 B（DB 绑定 store，用户可增删）
  UI/API 创建 VectorStore 行（表 vector_stores）
    → engine_factory.createEngineServiceFromStore()（engine_factory.go:56）
    → 按 EngineType 装配具体 repository
```

## 4. VectorStore 数据模型

`internal/types/vectorstore.go:39-56`：

```go
type VectorStore struct {
    ID          string           // UUID，主键
    TenantID    uint64           // 归属 workspace（多租户隔离）
    Name        string           // 友好名，如 "elasticsearch-hot"
    EngineType  RetrieverEngineType
    ConnectionConfig ConnectionConfig  // 连接参数（敏感字段 AES-GCM 加密）
    IndexConfig IndexConfig            // index/collection 命名与分片配置
    ...
}
```

关键设计：

1. **一个 tenant 可注册多个 VectorStore**（甚至同一引擎多个实例），用于多 store 场景（如 ES-hot + ES-warm 冷热分层，见 `vectorstore.go:36-38` 注释）。
2. **连接密钥加密**：`ConnectionConfig` 的 `Password`/`APIKey` 通过 `Value()`（`vectorstore.go:161-175`）在写库前用 AES-GCM 加密，`Scan()`（`:179-201`）读库后解密；API 返回前再 `MaskSensitiveFields()` 打码。
3. **IndexConfig 是引擎无关的配置合集**（`vectorstore.go:244-268`）：`IndexName`（ES/OpenSearch）、`CollectionPrefix`（Qdrant/Weaviate）、`CollectionName`（Milvus/TencentVectorDB）、`ShardNumber/ReplicationFactor`（Qdrant/Weaviate）、`ShardsNum/ReplicaNumber`（Milvus）、`BucketsNum/ReplicationNum`（Doris）、HNSW 参数（OpenSearch）。每个引擎只读自己关心的字段。
4. **命名优先级**：`ResolveCollectionName`（`vectorstore.go:433-446`）优先级 `CollectionPrefix > CollectionName > env var > 默认值`；`ResolveIndexName`（`:418-426`）`IndexConfig.IndexName > env var > 默认值`。

## 5. 引擎抽象层：KVHybrid 与 Composite

`internal/application/service/retriever/` 有两个核心类型：

### 5.1 KeywordsVectorHybridRetrieveEngineService（KVHybrid）

`keywords_vector_hybrid_indexer.go:47-52`：

```go
// NewKVHybridRetrieveEngine creates a new instance of the hybrid retrieval engine
// KV stands for KeywordsVector
```

**KV = Keywords + Vector**。它把「关键词检索」和「向量检索」封装成**一个引擎**：同一个 repository 同时实现 `KeywordsRetrieve` 和 `VectorRetrieve`，`Support()` 返回 `[KeywordsRetrieverType, VectorRetrieverType]`。每个物理引擎（Qdrant/ES/Milvus/...）都被包成这个 KVHybrid，然后塞进 registry。

### 5.2 CompositeRetrieveEngine

`composite.go:63-88`：吃一个 `[]RetrieverEngineParams{RetrieverType, RetrieverEngineType}`，把「哪种检索类型走哪个引擎」组装起来。这带来一个关键能力：

```go
// tenant.go:17-57 的 retrieverEngineMapping —— 每个 driver 展开成「类型→引擎」对
"elasticsearch_v7": { {Keywords, Elasticsearch}, },                          // 纯 BM25
"qdrant":          { {Keywords, Qdrant}, {Vector, Qdrant} },                // keyword+vector 都走 Qdrant
"elasticsearch_v8":{ {Keywords, Elasticsearch}, {Vector, Elasticsearch} },  // 都走 ES
```

默认（同 driver）keyword 和 vector 走**同一个引擎**；但配置层允许把两者拆开（例如 keyword→ES、vector→Qdrant），此时 `composite.go` 的 `Index` 会对每个注册引擎各写一份。这是唯一让 BM25 和向量物理分离的场景。

### 5.3 引擎解析：绑 store 还是回退 env

`retriever/factory.go:147-165` `CreateRetrieveEngineForKB`：

```go
if vectorStoreID == nil || *vectorStoreID == "" {
    // 未绑定 store → 回退 tenant 的 effective engines（RETRIEVE_DRIVER 驱动）
    return NewCompositeRetrieveEngine(registry, tenantInfo.GetEffectiveEngines())
}
// 绑定 store → 校验归属 + 从 registry 按 storeID 取引擎
return resolveBoundEngine(...)
```

`resolveBoundEngine`（`factory.go:194-260`）还带**归属校验**（`StoreOwnedBy`），跨租户访问返回 `ErrVectorStoreForbidden`；KB 一旦绑定某个 store，就用该 store 支持的全部检索类型，**覆盖 tenant 级默认路由**（`factory.go:250-258` 注释）。

## 6. 物理落点：命名规则与 KB 隔离

这是本文最关键的一节。**所有引擎都遵循同一条规律：物理分区键不是「知识库」，而是「嵌入维度」；不同 KB 靠一个 payload 字段隔离。**

### 6.1 collection/index 命名（按维度切分）

| 引擎 | 命名规则 | 代码 |
| --- | --- | --- |
| Qdrant | `collectionBaseName + "_" + dimension`，如 `weknora_embeddings_1536` | `qdrant/repository.go:50-52` |
| Weaviate | 同上（class 名按维度后缀） | `weaviate/repository.go:56` |
| Milvus | `getCollectionName(dimension)` | `milvus/repository.go:81-82` |
| Tencent VectorDB | `collectionName(dimension)` | `tencentvectordb/repository.go:491` |
| Doris | 表名按维度后缀 `prefix + "_" + dim` | `doris/repository.go` |
| Elasticsearch | **单 index**，不按维度（`xwrag_default` / `ELASTICSEARCH_INDEX`） | `elasticsearch/v8/repository.go:39` |
| OpenSearch | 单 index | 同 ES |
| Postgres / SQLite | 单表 | `postgres/repository.go` |

**Qdrant/Weaviate/Milvus/TencentVectorDB/Doris 是「按嵌入维度拆 collection」**：同一个嵌入模型（固定维度）的所有 chunk 进同一个 collection，只有换维度（换模型）才开新 collection。ES/OpenSearch/PG/SQLite 则连维度都不拆，单 index/表装一切。

### 6.2 KB 隔离靠 `knowledge_base_id` 字段

**没有「一个 KB 一个 collection」这回事。** 不同 KB 的向量混在同一个 collection 里，靠每个 point/doc 上的 `knowledge_base_id` 字段做查询期过滤：

```go
// qdrant/repository.go:500-501
must = append(must, qdrant.NewMatchKeywords(fieldKnowledgeBaseID, params.KnowledgeBaseIDs...))
// → 等价于 knowledge_base_id IN (kb1, kb2, ...)

// weaviate/repository.go:484 —— 同样的 fieldKnowledgeBaseID 用 ContainsAny
// elasticsearch/v8/repository.go:300-306 —— Terms 查询 knowledge_base_id
```

所以「跨库检索」在物理上就是**一次查询带 `IN (...)` 过滤**，而不是对每个 KB 各发一次。

### 6.3 FAQ 与文档不拆物理 collection

FAQ KB（`kb.Type == KnowledgeBaseTypeFAQ`）和文档 KB 在检索参数上是分开路由的（§9），但**物理上 FAQ chunk 和文档 chunk 同维度时在同一个 collection**，靠 `source_type` 字段区分。所有引擎的 `getCollectionName(dimension)` 都**不读 knowledgeType**——`knowledgeType` 只透传到 Delete/Copy 签名，不影响 collection 选择。

## 7. 关键词 vs 向量的物理形态

一句话纠正常见误解：**BM25 不是「存在某个单独的地方」，它是「对 content 字段算的相关性」**，和向量存在同一份文档里。各引擎对「关键词检索」的物理实现不同：

| 引擎 | 关键词检索物理形态 | 与向量是否同 store |
| --- | --- | --- |
| Qdrant | `content` 字段的 **full-text 索引**（Multilingual 分词），`NewMatchText` 匹配，非稀疏向量 | ✅ 同一 collection |
| Elasticsearch v7 | `content` 字段原生 **BM25**（v7 只配 keyword） | v7 无向量 |
| Elasticsearch v8 / OpenSearch | `content` 字段原生 **BM25**（`Match` 查询） | ✅ 同一 index |
| Weaviate | GraphQL `bm25` 算子 | ✅ 同一 class |
| Milvus | BM25 编码成**稀疏向量**字段 `text_bm25_emb`（`FunctionTypeBM25`） | ✅ 同一 collection |
| Tencent VectorDB | `BM25Encoder` 编码成**稀疏向量** | ✅ 同一 collection |
| Doris | 倒排索引 + `MATCH_ANY` | ✅ 同一表 |
| SQLite | FTS5 虚拟表 + `bm25()` 排名 | ✅ 同一库 |
| Postgres | pgvector 做向量 + FTS/ILIKE 做关键词 | ✅ 同一库 |

以 Qdrant 为例，一个 point（= 一个 chunk）长这样：

```text
weknora_embeddings_1536  （一个 collection 装所有 1536 维的 chunk）
  └─ point
       ├─ content           → text 字段 + 全文索引（关键词检索用）
       ├─ embedding         → dense 向量（向量检索用）
       ├─ knowledge_base_id → 隔离 KB
       ├─ chunk_id / knowledge_id / source_id / source_type / tag_id → 过滤/定位
       └─ is_enabled        → 软删除开关
```

建 collection 时，Qdrant 会为这些字段建 payload 索引，其中 `content` 建的是 **text 索引**（`TokenizerType_Multilingual`，支持中日韩），其余 ID 字段建 keyword 索引（`qdrant/repository.go:90-127`）。

## 8. 入库：Index / BatchIndex 写入路径

写入统一走 KVHybrid 的 `Index`/`BatchIndex`（`keywords_vector_hybrid_indexer.go`）：

```text
knowledge 处理流水线产出 []IndexInfo（content + chunk_id + knowledge_id + ...）
  → CompositeRetrieveEngine.BatchIndex（composite.go:212）
  → 对每个注册引擎各调一次 BatchIndex
      → KVHybrid.BatchIndex：
          if 引擎支持 VectorRetrieverType：
              embedder.Embed(content) → embedding
              写入 content + embedding
          else（纯 keyword）：
              只写 content（不 embed）
      → repository.BatchSave(ctx, indexInfoList, {embedding: ...})
```

关键点：

1. **embedding 只在「该引擎被分配了向量检索」时才生成**（`keywords_vector_hybrid_indexer.go:74-82`）——纯 keyword 引擎（如 ES v7）不 embed，只写文本。
2. **内容在写入前会 sanitize**：`sanitizeForEmbedding`（`:159-175`）剥离 base64 内联图片、按 `safetyMaxChars=20000` 字符截断，防止超大输入打爆 embedding API。
3. **批量写入并发有界**：`batchSize=40`、`maxConcurrency=5`，避免压垮后端。

## 9. 检索：路由与混合检索上限

检索入口 `HybridSearch`（`knowledgebase_search.go:93`）。核心是 `buildRetrievalParams`（`:352-441`）把「一个 store group 里的 KB」拆成三路检索参数：

```text
group 内的 KB（同 store）
  ├─ 向量路由：kb.IsVectorEnabled() && EmbeddingModelID != ""
  │     ├─ faqVectorKBIDs   （kb.Type == FAQ）→ KnowledgeType="faq"   → 一次向量检索
  │     └─ docVectorKBIDs   （其他）        → KnowledgeType=""        → 一次向量检索
  └─ 关键词路由：kb.IsKeywordEnabled() && kb.Type != FAQ
        └─ docKeywordKBIDs  → KeywordsRetrieverType → 一次关键词检索
```

于是**一次混合检索 = 最多 3 个 RetrieveParams**（doc 向量 + FAQ 向量 + doc 关键词），每个 param 里 `KnowledgeBaseIDs` 是一次性塞进去的一批 KB ID——所以「多库检索」在引擎内部就是一条带 `IN` 过滤的查询。

上限（`knowledgebase_search.go:15-19, 162-165`）：

```go
const maxRetrievalPoolSize = 500
matchCount := max(params.MatchCount*5, types.DefaultRetrievalTopK) * len(searchKBIDs)
if matchCount > maxRetrievalPoolSize { matchCount = maxRetrievalPoolSize }
```

即「每个 KB 想取 MatchCount 条 × 5 倍过检」的池子，最终封顶 500 条候选，跨库越多单库配额越薄。

## 10. 多 store 与跨库检索

当一次检索的 KB 分散在多个 VectorStore 上时，`resolveStoreGroups`（`knowledgebase_search_storegroup.go:86-147`）按 `(VectorStoreID, KB.TenantID)` 分桶：

```go
type partitionKey struct { storeID string; tenantID uint64 }
for _, kb := range kbs {
    sid := ""
    if kb.HasVectorStore() { sid = *kb.VectorStoreID }
    key := partitionKey{storeID: sid, tenantID: kb.TenantID}
    buckets[key] = append(buckets[key], kb)
}
```

- **分区键含 TenantID**：共享 KB（`kb.TenantID != 请求方租户`）的 store 归源租户所有，归属校验要对源租户做（`:22-28` 注释）。
- **store 解析有预算**：`storeResolveBudget = 12s`（`:20`），防止冷启动时多个 store 重建引擎把请求拖死。

fan-out 执行 `retrieveFromStores`（`knowledgebase_search_fanout.go:48-131`）：

| 限制 | 值 | 代码 |
| --- | --- | --- |
| 并发 store group 上限 | `defaultMultiStoreFanoutLimit = 4` | `:24, :67` |
| 每组超时 | `defaultMultiStoreRetrieveTimeout = 30s`（可 `MULTI_STORE_RETRIEVE_TIMEOUT_SEC` 覆盖） | `:22, :193-206` |
| 失败策略 | all-or-nothing：第一个 group 失败即整体失败 | `:32-37, :89-105` |
| 单 group 快路径 | `len(groups)==1` 直接返回，零 fan-out 开销 | `:56-58` |

**前置门控**：`validateSameEmbeddingModel`（`knowledgebase_search_storegroup.go:237-279`）强制跨库检索的所有 KB 共用同一个嵌入模型——这保证一次检索只会命中**一个维度**对应的 collection，不会出现「跨多个 collection 合并」的复杂度。

## 11. 分数归一化

当 fan-out 结果**跨越多个不同引擎类型**时（比如 keyword 走 ES、vector 走 Qdrant），各引擎的分数量纲不同，需要归一化到 [0,1] 再融合：

```go
// knowledgebase_search_fanout.go:110-129
if hasMixedEngineTypes(all) {
    for _, rr := range all {
        for _, hit := range rr.Results {
            hit.Score = normalizer.Normalize(ctx, hit.Score, rr.RetrieverType, rr.RetrieverEngineType)
        }
    }
}
```

**同一引擎**的结果保留原生量纲（可直接比）；跨引擎才归一化（`EngineAwareNormalizer` 对已知引擎有硬编码的分数尺度换算）。

## 12. 设计要点总结

1. **KVHybrid 抽象把「关键词+向量」压成单引擎**：不存在独立的 BM25 库，keyword 和 vector 是同一条记录的两种可检索物（`content` vs `embedding`）。这是整个存储层最重要的心智模型。
2. **物理分区键 = 嵌入维度，不是 KB**：Qdrant/Weaviate/Milvus/TencentVectorDB/Doris 按 `prefix_dim` 拆 collection；ES/PG/SQLite 单 index/表。换嵌入模型（维度变了）才换 collection。
3. **KB 隔离是查询期 filter，不是物理分桶**：`knowledge_base_id` 字段 `IN (...)` 过滤，跨库检索=一次带 IN 的查询。
4. **多 store 由 VectorStore 行抽象**：一个 tenant 可绑多个引擎/多实例（冷热分层），KB 通过 `VectorStoreID` 指针绑定；未绑定则回退 env 虚拟 store。
5. **安全处处设防**：连接密钥 AES-GCM 加密 + API 打码；SSRF 校验所有 store 地址；跨租户 store 访问拒绝；错误信息不回显 store UUID。
6. **可组合的「类型→引擎」路由**：`CompositeRetrieveEngine` 允许 keyword 和 vector 走不同引擎，是「BM25 与向量物理分离」的唯一开关。
7. **faq 与文档共用 collection**：`knowledgeType` 只影响检索参数路由，不改变物理落点。
