## 1. 检索质量的五个杠杆

WeKnora 的检索质量由五个相互独立的机制共同决定，顺序从底层到高层：

| 杠杆 | 作用层 | 核心文件 | 对质量的影响 |
| --- | --- | --- | --- |
| **分块策略** | 索引时 | `internal/infrastructure/chunker/` | 决定召回的基本粒度与上下文完整性，是质量根基 |
| **混合索引** | 索引时 | `internal/application/service/retriever/keywords_vector_hybrid_indexer.go` | 同一 chunk 同时入向量库 + 关键词库，互补召回 |
| **查询理解** | 检索前 | `chat_pipeline/query_understand.go` | 改写 query 消解指代、补全检索词，显著影响召回 |
| **混合检索 + RRF** | 检索中 | `knowledgebase_search.go`/`knowledgebase_search_fusion.go` | 向量语义 + 关键词精确匹配，RRF 融合排序 |
| **重排序 + MMR** | 检索后 | `chat_pipeline/rerank.go` | 精排 + 去冗余，决定最终喂给 LLM 的上下文质量 |

**质量公式（经验）**：`好分块 × 好 query 改写 × 混合召回 × 精排去重 = 高质量上下文`。任何一环薄弱都会在最终答案上放大误差。

**全景视角**：检索质量（五个杠杆）只是「问答质量」的一环。完整来看，WeKnora 从**三大维度七个层面**提升问答检索的质量和内容丰富度：

| 维度 | 层面 | 核心机制 | 说明位置 |
| --- | --- | --- | --- |
| **检索质量** | 分块 / 索引 / 查询理解 / 混合召回 / 精排 | 上文五个杠杆 | 本文 §2~§10 详述 |
| **内容丰富度** | 上下文组装 | 父块解析 + 相邻块扩展（§9）、FAQ 快路径（§10） | 本文 |
| 内容丰富度 | 知识图谱 | Neo4j 实体关系补召回（第三条召回通道） | 《知识图谱生成与使用逻辑》 |
| 内容丰富度 | 图片多模态 | OCR + VLM caption，图片内容参与检索 | 《不同格式文档处理流程》§8 |
| 内容丰富度 | 表格摘要 | DuckDB + LLM 表摘要/列描述，结构化数据可检索 | 《文档入库处理流程》§7 |
| 内容丰富度 | 网页搜索 | 外部实时信息补充 | 《问题检索与QA回答流程》 |
| **内容治理** | 分块编辑 | 修订历史 + 回滚 + 重索引，人工修正检索内容 | 《文档分块展示与编辑功能》 |

> 本文以「检索质量」为主线（§2~§10），「内容丰富度」和「内容治理」的详细机制交叉引用到对应文档。

## 2. 分块策略（质量根基）

分块配置类型 `ChunkingConfig`（`internal/types/knowledgebase.go:244`）：

```go
type ChunkingConfig struct {
    ChunkSize      int      // 分块大小（字符数）
    ChunkOverlap   int      // 分块重叠（字符数）
    Separators     []string // 分隔符优先级
    EnableParentChild bool   // 父-子分块开关
    ParentChunkSize int      // 父块大小（默认 4096）
    ChildChunkSize  int      // 子块大小（默认 384，用于 embedding）
    Strategy       string    // legacy / auto / heading / heuristic / recursive
    TokenLimit     int       // 按 token 近似上限（0=用 ChunkSize 按字符）
    Languages      []string  // 启发式语言提示
}
```

默认值（`config/config.yaml:41`）：

```yaml
knowledge_base:
  chunk_size: 512
  chunk_overlap: 50
  split_markers: ["\n\n", "\n", "。"]   # 递归分隔符优先级：段落 → 行 → 中文句号
```

### 2.1 自适应分块策略（Strategy）

`internal/infrastructure/chunker/`实现了多级自适应分块，由`Strategy` 字段选择：

| Strategy | 实现文件 | 说明 |
| --- | --- | --- |
| `legacy` | 历史递归分块 | 按`Separators` 递归切分 |
| `heading` | `heading_splitter.go` | 按标题层级切分（Markdown 标题），保留面包屑路径（breadcrumb） |
| `heuristic` | `heuristic_splitter.go` | 按语义边界启发式切分（换页符、编号章节、中/德文章节标记等） |
| `recursive` | 递归切分 | 无结构文档的回退方案 |
| `auto` | `profiler.go` | 先剖析文档结构（DocProfile），再自动选择 heading/heuristic/recursive |

**质量要点**：

- **标题感知分块**（heading）对结构化文档（Markdown/技术文档）显著优于纯长度切分，因为它保留了「章节边界」与「面包屑路径」（父标题链），召回片段自带上下文。
- **超长块递归降级**：切分器遇到超过 `ChunkSize` 的块时，会递归进入下一级更细的分隔符。
- **代码块保护**：标题切分会忽略代码围栏（code fence）内的 `#`，避免误切。

### 2.2 父-子分块（Parent-Child，检索质量关键）

`EnableParentChild = true` 时启用经典的两级分块：

- **父块（ParentChunkSize，默认 4096 字符）**：大粒度，提供完整上下文；
- **子块（ChildChunkSize，默认 384 字符）**：小粒度，用于向量匹配。

**核心机制**（注释原文）：*"Retrieval matches on child but returns parent content"* —— **用小子块做向量匹配，命中后返回父块内容**。这解决了「块太大则召回不精确、块太小则上下文断裂」的两难：

```text
文档
 ├─ 父块 A (4096 字符，完整上下文)
 │   ├─ 子块 A1 (384 字符，被 embedding)  ← 向量检索匹配到 A1
 │   ├─ 子块 A2 (384 字符，被 embedding)
 │   └─ 子块 A3 (384 字符，被 embedding)
 └─ 父块 B (4096 字符) ...
```

检索命中 A1 → 返回整个父块 A 的内容。这就是 `merge.go`里`resolveParentChunks` 做的事（见 §9）。

**自研建议**：父-子分块是 RAG 检索质量提升最直接的杠杆之一，建议默认开启，父块/子块比例约 8~16 倍。

> **父块的定位**：父块（`parent_text`）是**纯上下文块**——只写 DB 供检索时反查，**不参与 embedding 向量索引、关键词索引，也不参与问题生成/图谱抽取/摘要等异步富化**。详细结论见《文本解析分块详解.md》§6.4。

## 3. 索引构建：什么被向量化、什么被关键词化

文件：`internal/application/service/retriever/keywords_vector_hybrid_indexer.go`

### 3.1 混合索引：同一内容双写入

`Index`/`BatchIndex`中，当 retriever 类型包含`VectorRetrieverType` 时，会**对同一 chunk 内容同时**：

1. 调 `embedder.Embed(content)` 生成向量，写入向量库；
2. 将原文写入关键词索引（BM25/全文检索，由底层引擎负责）。

也就是说，**混合索引不是两套不同的内容，而是同一内容同时进两条检索通道**。这样向量检索（语义）和关键词检索（精确匹配）天然互补。

### 3.2 嵌入前的清洗（sanitizeForEmbedding）

```go
const safetyMaxChars = 20000  // 单条 embedding 输入的绝对上限
```

- **base64 图片清洗**：内联 base64 图片 payload 会被正则替换为 `[image]`（避免把图片二进制编码进语义向量）；
- **超长截断**：超过 20000 字符（rune 数）会截断并告警（防止打爆 embedding API）。

### 3.3 批量索引与重试

- `BatchEmbedWithPool` 分批（`batchSize = 40`）并发 embedding；
- 指数退避重试：`embedRetryAttempts = 5`，`embedRetryBaseDelay = 200ms`（200/400/800/1600/3200ms）。

### 3.4 ChunkType（决定索引到哪个库）

`internal/types/chunk.go` 定义了多种 chunk 类型，不同类型走不同索引：

| ChunkType | 含义 | 检索用途 |
| --- | --- | --- |
| `text` | 普通文本块 | 文档向量库 |
| `parent_text` | 父块文本 | 父-子分块时返回给 LLM 的上下文 |
| `image_ocr`/`image_caption` | 图片 OCR / 描述 | 多模态，图片内容参与向量匹配 |
| `summary` | 文档摘要块 | 概览类召回 |
| `entity`/`relationship` | 实体 / 关系 | 知识图谱（Neo4j） |
| `faq` | FAQ 条目 | **独立 FAQ 向量索引**（见 §10） |
| `table_summary`/`table_column` | 表格摘要 / 列 | 表格检索（DATA_ANALYSIS 用） |
| `wiki_page` | Wiki 页面 | Wiki 模式 |

### 3.5 生成问题（Generated Questions，HyDE 式）

索引阶段可用 LLM 为每个 chunk **预生成若干问题**（`generate_questions_prompt_id`→`prompt_templates/generate_questions.yaml`），存入 `ChunkMetadata`。检索时：

- 这些生成问题在**重排阶段**（`getEnrichedPassage`）被拼进 passage，增强重排模型的语义信号（见 §8）；
- FAQ 的相似问句（standard/similar question）也是这个机制。

**自研建议**：`生成问题` 是一种「**索引期 query 增强**」，相当于把未来用户可能怎么问，提前写进 chunk 的可匹配文本里，对口语化提问召回提升明显。

## 4. 查询理解：改写 + 意图分类

文件：`internal/application/service/chat_pipeline/query_understand.go`

检索前，`QUERY_UNDERSTAND` 阶段用 LLM 对原始 query 做两件事：

1. **改写（rewrite）**：结合对话历史，把口语化/指代不明的问题改写为适合检索的查询。例如 *"那个东西怎么配？"* → *"WeKnora 如何配置向量数据库"*。
2. **意图分类（intent）**：输出 `QueryIntent`（`internal/types/chat_manage.go:86`）：

```go
IntentKBSearch      = "kb_search"      // 知识库检索
IntentWebSearch     = "web_search"     // 网页搜索
IntentGreeting      = "greeting"       // 问候
IntentChitchat      = "chitchat"       // 闲聊
IntentFollowUp      = "follow_up"      // 追问
IntentImageOnly     = "image_only"     // 纯图片
IntentSummarize     = "summarize"      // 总结
IntentClarification = "clarification"  // 澄清
```

输出结构：`{"rewrite_query": "...", "intent": "kb_search", "image_description": "..."}`。

**质量要点**：

- **改写用的 query 才是真正检索的 query**（`chatManage.RewriteQuery` 贯穿后续检索与重排）。所以「改写模型」的质量直接决定召回。
- 非检索意图（`greeting`/`chitchat`/`image_only`/`doc_only`）会**跳过检索**（`NeedsRetrieval()` 返回 false），直接走纯 chat。
- **长期记忆背景注入**（`memoryBackground`）：把「提问者是谁、长期关注什么」作为 `<asker_background>` 注入改写 prompt，让改写「站在提问者视角消解指代」——例如做医学影像的人和做自动驾驶的人问 "如何调分割" 会得到不同改写。这是**检索前**的记忆应用（区别于记忆召回阶段）。
- 改写模型选择：有图片优先视觉模型，其次 `QueryUnderstandModelID`，回退 `ChatModelID`。

## 5. 混合检索：向量 + 关键词 + RRF

入口：`internal/application/service/knowledgebase_search.go`的`HybridSearch`（第 93 行）。

### 5.1 HybridSearch 完整流程

```text
HybridSearch(id, params)
 ├─ 1. 归一化 MatchCount（≤0 回退 DefaultRetrievalTopK=50）
 ├─ 2. 确定检索 KB 集合（多 KB 合并 / 单 KB）
 ├─ 3. 批量加载 KB + authorizeKBAccess + validateSameEmbeddingModel
 ├─ 4. pickPrimary（定 embedding 模型 + FAQ 类型）
 ├─ 5. 过度召回：matchCount = max(MatchCount*5, 50) * len(KBs)，上限 500
 ├─ 6. 计算 query embedding（仅一次，跨 KB 复用）
 ├─ 7. resolveStoreGroups（按 storeID+租户分组，绑定向量库引擎）
 ├─ 8. buildRetrievalParams（FAQ向量/文档向量/文档关键词 三类参数）
 ├─ 9. retrieveFromStores → CompositeRetrieveEngine.Retrieve（并发分发）
 ├─ 10. classifyRetrievalResults（向量/关键词分开）
 ├─ 11. fuseOrDeduplicate（RRF 融合 或 去重）
 ├─ 12. applyFAQPostProcessing（FAQ 迭代 TopK）
 ├─ 13. 截断到 MatchCount
 └─ 14. processSearchResults（上下文富化：父块/相邻块/图片）
```

### 5.2 过度召回（Over-Retrieval）

```go
matchCount := max(params.MatchCount*5, types.DefaultRetrievalTopK) * len(searchKBIDs)
if matchCount > maxRetrievalPoolSize { matchCount = maxRetrievalPoolSize }  // 500
```

**设计意图**：先召回 **5 倍** 候选池（下限 50，上限 500），交给重排阶段裁剪。这是「粗召回 + 精排」的经典两段式。

### 5.3 向量 + 关键词参数构建（buildRetrievalParams）

按 KB 类型分区路由（`knowledgebase_search.go:352`）：

- **FAQ KB** → 只进 FAQ 向量索引（无关键词索引）；
- **文档 KB** → 进默认向量索引 + 关键词索引；
- 混合组（同一 embedding 模型下有 FAQ + 文档）→ 每个索引各一条 `RetrieveParams`。

```go
// 向量检索参数
RetrieveParams{ Query, Embedding, TopK: matchCount, Threshold: VectorThreshold,
                RetrieverType: VectorRetrieverType, KnowledgeType: "faq" | "" }
// 关键词检索参数
RetrieveParams{ Query, TopK: matchCount, Threshold: KeywordThreshold,
                RetrieverType: KeywordsRetrieverType }
```

### 5.4 RRF 融合（fuseWithRRF）

文件：`knowledgebase_search_fusion.go:84`

```go
// RRF score = vectorWeight/(k+vectorRank) + keywordWeight/(k+keywordRank)
rrfScore := 0.0
if rank, ok := vectorRanks[chunkID]; ok {
    rrfScore += vectorWeight / float64(rrfK+rank)
}
if rank, ok := keywordRanks[chunkID]; ok {
    rrfScore += keywordWeight / float64(rrfK+rank)
}
```

- **仅向量**或**仅关键词** → 简单按分去重（`deduplicateByScore`）；
- **两者都有** → RRF 融合。

**RRF 参数**（`RetrievalConfig`，`retrieval_config.go`）：

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `RRFK` | 60 | 平滑常数，越大曲线越平（降低 top-1 偏向），建议 30~100 |
| `RRFVectorWeight` | 0.7 | 向量权重 |
| `RRFKeywordWeight` | 0.3 | 关键词权重 |

**质量要点**：RRF 是**基于排名（rank）而非原始分数**的融合，因此天然免疫「向量分与关键词分尺度不一致」的问题——这正是 §6 评分归一化只归一化向量分、关键词分 passthrough 的原因。

## 6. 评分归一化（跨引擎）

文件：`internal/application/service/retriever/normalizer.go`

不同向量库引擎返回的余弦相似度范围不同，跨引擎混合检索时必须先归一化到统一 `[0, 1]` 尺度。

`EngineAwareNormalizer.Normalize` 的分组：

| 引擎 | 原始分数范围 | 归一化公式 |
| --- | --- | --- |
| **Milvus** | `[-1, 1]`（COSINE metric） | `(score + 1) / 2` |
| Elasticsearch v8 | `[0, 1]`（Lucene script_score 非负） | passthrough + clamp01 |
| OpenSearch | `[0, 1]`（k-NN COSINESIMIL 已预转换） | passthrough + clamp01 |
| Weaviate | `[0, 1]`（certainty 内蕴） | passthrough + clamp01 |
| pgvector / sqlite-vec / Qdrant / TencentVectorDB / Doris | `[0, 1]`（IR 归一化向量经验值） | passthrough + clamp01 |

**关键点**：

- **只归一化向量分**。关键词（BM25）分数范围无界，重缩放会压扁长尾，而 RRF 基于排名、对尺度免疫，所以 BM25 分直接 passthrough。
- **`clamp01`**：把 NaN/Inf 也安全地钳到 `[0,1]`（NaN 会破坏排序的严格弱序）。
- **仅在跨引擎时归一化**（`hasMixedEngineTypes`）：同引擎结果保持原生尺度，直接可比；单 store 走 fast path 零开销（见 `knowledgebase_search_fanout.go`）。

## 7. 查询扩展（低召回补救）

文件：`internal/application/service/chat_pipeline/query_expansion.go`

当初始召回数 `< EmbeddingTopK`时触发`runQueryExpansion`。这是**纯本地、无 LLM** 的扩展，成本低、速度快。

### 7.1 扩展策略（expandQueries）

生成最多 5 个 query 变体：

1. **去停用词**：`extractKeywords` 去掉中英停用词（的/是/了/a/the/is/are/...），保留关键词；
2. **引号短语提取**：抽出 `"..."` `「...」` 中的精确短语；
3. **分隔符切分**：按 `,，;；、。！？!?` 切分，取最长片段；
4. **去问句词**：移除「什么是/如何/怎么/为什么/哪个/请告诉我」等（`questionWords` 正则）。

中文分词用 **Jieba 搜索模式**（`types.Jieba.CutForSearch`，搜索模式会切出更细的词）。

### 7.2 扩展检索参数

```go
expTopK := max(chatManage.EmbeddingTopK*2, chatManage.RerankTopK*2)  // TopK 翻倍
expKwTh := chatManage.KeywordThreshold * 0.8                         // 关键词阈值放宽 20%
```

**质量要点**：查询扩展是**召回兜底**——当改写后的 query 召回太少时，用更宽松的变体补召回。放宽关键词阈值（×0.8）+ 翻倍 TopK，是为了「宁可多召回、交给重排筛」。

## 8. 重排序：模型分 + 复合分 + MMR

文件：`internal/application/service/chat_pipeline/rerank.go`

### 8.1 重排流程

1. 取重排模型 `GetRerankModel`。
2. **构造 enriched passage**（`getEnrichedPassage`）：
   - `cleanPassageForRerank`剥离 markdown 噪声（图片、URL、表格分隔符、标题`#`、粗斜体、列表标记、HTML 标签），保留语义文本；
   - 追加图片 caption / OCR 文本、生成问题（`GeneratedQuestions`）。
3. 调 `rerankModel.Rerank(query, passages)` 得相关性分。
4. **阈值过滤**（`rerank`）：
   - `RelevanceScore >= RerankThreshold` 才保留；
   - 无结果 → **阈值降级**（×0.7，下限 0.3）重试；
   - 仍无 → **top-1 兜底**（最高分 ≥ `fallbackMinScore`时保留一条；显式作用域下`fallbackMinScore=0`）。
5. **复合分** `compositeScore`：

```text
   composite = 0.6 * modelScore + 0.3 * baseScore + 0.1 * sourceWeight
   ```

- `modelScore`：重排模型分；
- `baseScore`：检索阶段分（RRF 或向量分）；
- `sourceWeight`：网页来源 0.95，其余 1.0。

1. **FAQ 提权**（可选）：`FAQScoreBoost` 乘到 FAQ 分块分数上。
2. **MMR 去冗余** `applyMMR`（`lambda = 0.7`）。

### 8.2 MMR（Maximal Marginal Relevance）

```go
mmr = lambda*relevance - (1.0-lambda)*redundancy   // lambda = 0.7
```

- `relevance`：chunk 的相关性分；
- `redundancy`：与已选 chunk 的最大 Jaccard 相似度（基于 token 集合）；
- 贪心选出 `RerankTopK` 个「相关且彼此不重复」的结果。

**质量要点**：MMR 解决「召回结果高度重复」问题——避免喂给 LLM 一堆内容重叠的 chunk，浪费上下文窗口。`lambda=0.7` 偏向相关性、适度惩罚冗余。

### 8.3 失败兜底

重排 API 失败 → 直接回退原始检索结果（`api_error_fallback`），保证流水线不中断、仍能返回答案。

## 9. 分块合并：父块解析 + 相邻块扩展

文件：`internal/application/service/chat_pipeline/merge.go`

`PluginMerge.OnEvent` 的 8 步（`merge.go:44`）：

1. **选输入**：优先 `RerankResult`，空则回退 `SearchResult`（按分降序）。
2. **初始去重**（ID + 内容签名）。
3. **注入历史引用**（历史轮次引用过的知识片段）。
4. **解析父块** `resolveParentChunks`：子块 → 父块，补全上下文（对应 §2.2 父-子分块）。
5. **按知识源 + 分块类型分组，合并相邻正文**。
6. **填充 FAQ 答案** `populateFAQAnswers`。
7. **扩展短上下文** `expandShortContextWithNeighbors`：用相邻块补足过短上下文。
8. **最终去重**：ID + 签名 + 部分内容重叠（`removePartialOverlaps`，token 重叠系数 ≥ 0.85 视为冗余）。

**质量要点**：

- **父块解析**让「小子块命中 → 大父块喂 LLM」成为可能；
- **相邻块扩展**解决「答案跨块边界」的问题；
- **部分重叠移除**（`removePartialOverlaps`）进一步去重，比精确签名去重更强——能抓跨知识库的近似重复。

## 10. FAQ 快路径

FAQ 型知识库走**独立向量索引 + 直接答案**的优化路径：

- **独立 FAQ 向量索引**：FAQ 条目（问-答对）单独建向量库，检索时按 `KnowledgeType = "faq"` 路由（`buildRetrievalParams`）；
- **直接答案阈值** `FAQDirectAnswerThreshold`：FAQ 命中且分数 ≥ 阈值时，`match="exact"` 高置信直接回答（`into_chat_message.go`）；
- **FAQ 提权** `FAQScoreBoost`：重排时对 FAQ 分块分数乘 boost；
- **迭代 TopK**：FAQ 召回不足时，`applyFAQPostProcessing` 逐轮扩大 TopK 重新召回（见 §5.1 步骤 12）。

**质量要点**：FAQ 场景是「精确匹配优先」，所以有独立索引 + 直接答案 + 提权三条优化。对自研来说，FAQ/客服场景值得单独建「问-答索引」，与文档 RAG 分离。

## 11. Agent 检索工具（Agentic 检索）

文件：`internal/agent/tools/knowledge_search.go`（语义检索）、`grep_chunks.go`（关键词检索）、`query_knowledge_graph.go`（图谱检索）。

Agent 模式下，检索是 LLM 主动调用的**工具**，而非固定流水线。

### 11.1 knowledge_search（语义检索工具）

- **多 query 语义检索**：`queries` 参数接收 **1~5 个语义问题/概念陈述**（不是关键词列表），LLM 把复杂意图拆成多个语义 query 并行检索；
- **召回合并 + 重排 + MMR**：复用 `HybridSearch` 召回，重排模型打分，MMR 去冗余；
- **seenChunks 去重**：同一 session 内重复调用时，已返回过的 chunk 以紧凑形式呈现，避免 LLM 重复读相同内容（省 token）。

### 11.2 工具分工（提升检索质量的工具设计）

| 工具 | 检索类型 | 适用场景 |
| --- | --- | --- |
| `knowledge_search` | 语义/向量 | 概念解释、意图检索、how/why 问题 |
| `grep_chunks` | 关键词/正则 | 精确字面匹配、错误码、实体名 |
| `query_knowledge_graph` | 图谱（Neo4j） | 实体关系、多跳推理 |
| `list_knowledge_chunks` | 列分块 | 定位某文档的具体分块 |
| `web_search` | 网页 | 外部信息 |
| `search_memory`/`search_conversations` | 记忆/历史 | 长期记忆、历史会话 |

**Agentic RAG 的关键洞察**：把「语义检索」和「关键词检索」拆成**两个独立工具**，让 LLM 根据任务类型选择。语义检索工具的 description 里明确写了它**不做什么**（不做精确关键词匹配、不查错误码、不查实体），并引导 LLM 用另一工具做字面检索。这种「工具能力边界清晰化」是 Agentic RAG 检索质量的重要一环。

## 12. 可调参数速查表

### 12.1 检索参数（`RetrievalConfig`，租户级，JSONB 存储，UI 可改）

| 参数 | 默认值 | 调优建议 |
| --- | --- | --- |
| `EmbeddingTopK` | 50 | 召回候选数；召回质量差时可加大（配合重排） |
| `VectorThreshold` | 0.15（类型默认）/ 0.2（config.yaml） | 向量相似度下限；过低→噪声，过高→漏召回 |
| `KeywordThreshold` | 0.3 | 关键词匹配下限 |
| `RerankTopK` | 10（类型默认）/ 30（config.yaml） | 精排后保留数 = **最终送入 LLM 的分块数（硬限制）** |
| `RerankThreshold` | 0.2（类型默认）/ 0.3（config.yaml） | 重排分下限 |
| `RRFK` | 60 | RRF 平滑常数，30~100 |
| `RRFVectorWeight` | 0.7 | 向量权重 |
| `RRFKeywordWeight` | 0.3 | 关键词权重 |

### 12.2 会话/流水线参数（`config.yaml` `conversation`）

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `max_rounds` | 5 | 历史轮数（0 = 关闭多轮） |
| `enable_rewrite` | true | 查询改写 |
| `enable_query_expansion` | true | 低召回查询扩展 |
| `enable_rerank` | true | 重排序 |
| `fallback_strategy` | model | 无结果时的兜底（model/fixed） |
| `summary.temperature` | 0.3 | 答案生成温度 |
| `summary.max_completion_tokens` | 2048 | 答案最大 token（输出 token 上限，非字符限制） |
| `summary.max_input_chars` | 16384 | **仅用于文档摘要生成**的输入截断，非 QA 回答 |

> **预算澄清**：最终送入 LLM 的分块数 = `RerankTopK`（硬限制）；QA 回答输出上限 = `max_completion_tokens`（2048 token，≈中文 3000~4000 字），**流式回答无字符级截断**；QA 上下文字符无硬上限（由 `RerankTopK × chunk_size` 决定，≈15K 字符）。`max_input_chars = 16384` 只作用于文档摘要（`sampleLongContent`），不是 QA。Agent 工具输出上限 `DefaultMaxToolOutput = 24000` 字符，上下文窗口 80% 触发压缩。

### 12.3 分块参数（`config.yaml` `knowledge_base`）

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `chunk_size` | 512 | 分块字符数 |
| `chunk_overlap` | 50 | 分块重叠 |
| `split_markers` | `["\n\n", "\n", "。"]` | 递归分隔符 |
| `ParentChunkSize` | 4096 | 父块大小（父-子分块时） |
| `ChildChunkSize` | 384 | 子块大小（父-子分块时） |

## 13. 自研 Agentic RAG 的复用要点

把 WeKnora 的实践提炼为可复用的设计决策：

### 13.1 必做（高性价比）

1. **父-子分块**：小子块匹配、大父块喂 LLM，解决粒度两难。
2. **混合索引**：同一内容同时入向量库 + 关键词库（BM25），互补召回。
3. **RRF 融合**：基于排名融合向量/关键词结果，天然免疫尺度不一致。
4. **过度召回 + 精排**：先召回 5 倍候选（cap 上限），再重排裁剪。
5. **重排模型 + MMR**：精排去冗余，避免上下文重复浪费窗口。
6. **query 改写**：检索前用 LLM 改写口语化/指代不清的 query。
7. **跨引擎评分归一化**：统一到 `[0,1]`，关键词分 passthrough（RRF 免疫）。

### 13.2 强烈建议（进一步提升）

1. **生成问题（HyDE 式）**：索引期预生成问题，增强可匹配文本。
2. **查询扩展兜底**：本地无 LLM 扩展（去停用词/去问句词/分词），低召回时补召回。
3. **工具能力边界清晰化**：语义检索 vs 关键词检索拆成独立工具，让 Agent 按任务选择。
4. **FAQ 独立索引**：问-答对单独建库，精确匹配优先 + 直接答案阈值。
5. **标题感知分块**：结构化文档按标题层级切分（带面包屑路径）。
6. **长期记忆注入改写**：让 query 改写站在提问者视角消解指代。

### 13.3 工程细节（可借鉴）

1. **embedding 只算一次**：同一 embedding 模型的多个 KB 共享一次 query embedding，省 API 调用。
2. **失败兜底**：重排 API 失败 → 回退原始检索结果；阈值无结果 → 降级重试 → top-1 兜底。流水线永不因单点失败中断。
3. **输入清洗**：base64 图片 → `[image]`，超长截断（20000 字符），防 embedding API 异常。
4. **指数退避重试**：embedding 调用 5 次重试，200ms 起步。
5. **内容签名 + 部分重叠去重**：精确签名去重 + token 重叠系数（≥0.85）去冗余。

## 附：检索全链路时序（质量视角）

```text
用户 query（口语化）
  │ ① 查询理解：LLM 改写 + 意图分类 + 记忆背景注入
  │     └─ RewriteQuery（这才是真正检索的 query）
  ▼
  │ ② 混合检索（HybridSearch）
  │     ├─ query embedding（一次）
  │     ├─ 向量检索 ──┐
  │     ├─ 关键词检索 ─┤ 并行，跨引擎评分归一化
  │     │              ├─ RRF 融合（k=60, 向量0.7/关键词0.3）
  │     │              └─ 阈值过滤 + 过度召回截断
  │     └─ 低召回 → 查询扩展（本地，放宽阈值 ×0.8）
  ▼
  │ ③ 重排序（rerank 模型 + 复合分 + MMR λ=0.7）
  │     └─ 阈值降级 / top-1 兜底
  ▼
  │ ④ 合并（父块解析 + 相邻块扩展 + 去重）
  ▼
  │ ⑤ 上下文模板组装 → LLM 流式生成答案
```
