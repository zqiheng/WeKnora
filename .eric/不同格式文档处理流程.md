# WeKnora 不同格式文档的处理流程

> 本文回答：**Word / PDF / Excel / PPT 等不同格式的文件，各自是怎么被解析成 Markdown 的**。
>
> 解析主体是 `docreader/`（Python gRPC 服务），核心思想：**每种格式有一个独立的 Parser，把文件统一转换为 Markdown + 图片引用**，再由 WeKnora 主服务（Go）做分块、索引、OCR、VLM。
>
> 代码基准：`docreader/parser/`（解析器）+ `internal/infrastructure/docparser/`（Go 侧引擎路由）。

## 1. 统一流程：格式 → 引擎 → 解析器 → Markdown

所有格式走同一条链路（`internal/application/service/knowledge_process.go` 的 `ProcessDocument` → `convert`）：

```text
上传文件（bytes + file_type）
  │
  ▼
① 引擎路由（resolveDocReader）：按 file_type + ParserEngineRule 选引擎
  │   builtin（默认）/ markitdown / opendataloader / MinerU / anydoc / PaddleOCR-VL
  ▼
② 格式嗅探（detect_effective_file_type）：检查 magic bytes，纠正「改名文件」
  │   例：.docx 扩展名但内容是 OLE 二进制 → 路由到 doc 解析器
  ▼
③ 解析器选择（registry.get_parser_class）：引擎 + 有效格式 → Parser 类
  ▼
④ 解析（parser.parse）：格式 → Markdown + 图片引用
  │   docreader 只做格式转换，不做分块/OCR/VLM
  ▼
⑤ 回到 Go：分块 → 建索引 → 多模态（OCR/VLM）/ ASR
```

**关键设计**：docreader 的 `BaseParser` 注释明确写——*"BaseParser only extracts markdown text and raw image references. Chunking, image storage, OCR, and VLM caption are handled by the Go App module."* 解析、分块、OCR 三件事解耦。

## 2. 格式 → 解析器映射表

来源：`docreader/parser/registry.py`（`BUILTIN_ENGINE` 注册表）。

| 格式（扩展名） | 解析器 | 依赖库 | 说明 |
| --- | --- | --- | --- |
| `docx` | `Docx2Parser`（FirstParser[MarkitdownParser, DocxParser]） | MarkItDown 优先 + python-docx 兜底 | 现代 Word（OOXML） |
| `doc` | `DocParser` | textract + LibreOffice | 旧版二进制 Word（OLE） |
| `pdf` | `PDFParser` | pypdfium2 | 逐页路由（文本/扫描） |
| `md` / `markdown` | `MarkdownParser` | — | Markdown 直接处理 |
| `xlsx` / `xls` | `ExcelParser` | pandas + openpyxl | 表格 → 结构化文本 |
| `pptx` / `ppt` | `MarkitdownParser` | MarkItDown + LibreOffice | 演示文稿 |
| `epub` | `EPUBParser` | ebooklib + BeautifulSoup | 电子书 |
| `html` / `htm` | `HTMLParser` | BeautifulSoup | 静态 HTML |
| `mhtml` | `MHTMLParser` | email + BeautifulSoup | 网页存档 |
| `xmind` | `XMindParser` | — | 思维导图 |
| `jpg`/`png`/`gif`/`bmp`/`tiff`/`webp` | `ImageParser` | — | 图片（OCR/VLM 在 Go） |
| `csv`/`txt` | Go `SimpleFormatReader` | — | 简单文本格式，Go 直接处理 |

> **特殊格式**：`csv`、`txt`、`md` 等简单格式，Go 侧的 `SimpleFormatReader`（`builtin_converter.go`）直接处理，**不经过 Python docreader**（`simpleFormats` 白名单）。

## 3. Word：docx / doc

### 3.1 docx（现代 Word，OOXML）

`Docx2Parser` 是 `FirstParser`（`_parser_cls = (MarkitdownParser, DocxParser)`，`docx2_parser.py:11`）—— **先试 `MarkitdownParser`，失败回退 `DocxParser`**。

`DocxParser`（`docx_parser.py`，56KB）：

- 用 `python-docx` 解析 OOXML；
- **多进程并发分页**（`ProcessPoolExecutor`，处理超大文档）；
- 提取正文 + 表格 + 图片 + 合并单元格（`docx_merge.py` 的 `fill_vertical_merged_cells_docx`）。

### 3.2 doc（旧版二进制 Word，OLE）

`DocParser`（`doc_parser.py`）：

- 用 `textract`（或 LibreOffice 转换）提取文本；
- 通过 `SandboxExecutor` 在沙箱中执行转换命令（带代理配置）；
- **继承自 `Docx2Parser`**（`class DocParser(Docx2Parser)`），复用 docx 的处理逻辑。

### 3.3 格式嗅探（关键）

`parser.py` 的 `detect_effective_file_type`：有些 WPS/Word 文件是**旧版 OLE 格式但被改名为 .docx**。通过检查 magic bytes（OLE Compound File = `\xd0\xcf\x11\xe0\xa1\xb1\x1a\xe1`）识别，把「假 .docx」路由到 doc 解析器，避免把二进制 OLE 喂给 DOCX 解析器。

## 4. PDF：逐页路由（文本页 vs 扫描页）

`PDFParser`（`pdf_parser.py`，57KB）是**最复杂的解析器**，设计对齐 MinerU / Docling / DeepDoc：

### 4.1 逐页分类

对 PDF 的**每一页独立分类**为「原生文本页」或「扫描图片页」：

- **判断信号 = 图片面积覆盖率**（图片 bbox 面积 / 页面面积），**不是字符数**。扫描页本质是一张覆盖整页的大图，即使带低质量的嵌入 OCR 文本层，也不能信任它；
- 阈值 `SCAN_IMAGE_AREA_RATIO = 0.5`（图片覆盖 >50% 页面面积 → 扫描页）；原生数字页约 0.0-0.05，扫描页约 1.0+；
- 辅助信号 `SCAN_MIN_CHARS_PER_PAGE = 10`（低于此字符数视为无可用文本层）。

### 4.2 两种页的处理

- **原生文本页** → 提取文本层，并做**版面感知的阅读顺序重建**（`LAYOUT_ORDERING`）：
  - 几何 XY-cut 切割，多栏页面**逐栏线性化**而非逐行交错；
  - 词间距空白插入（`WORD_GAP_WIDTH_RATIO = 0.4`）；
  - 标题检测（字号代理 = rect 高度相对页面中位行高，`DETECT_HEADINGS`）；
  - 过滤隐藏文本（render-mode 3，防隐藏文本注入）、页边水印列（arXiv 水印）。
- **扫描图片页** → **渲染为 JPEG，打标 `image_source_type=scanned_pdf`**，交给 Go App 做 OCR/VLM（docreader 自己**不做 OCR**）。

### 4.3 嵌入图片提取

原生页里嵌入的图表/图片会被提取为图片引用（交给 Go OCR/caption），按尺寸/页面面积占比/跨页重复率过滤 logo、图标、水印（`EMBED_MIN_PIXELS=80`、`EMBED_REPEAT_PAGE_FRAC=0.5`、`EMBED_MAX_IMAGES=50`）。

### 4.4 并发限制

pdfium（pypdfium2 的 C 库）进程级非线程安全，所有 PDF 操作（文本提取/页面渲染/图片提取）被 `_PDFIUM_LOCK` 全局锁串行化，避免两个 gRPC worker 线程同时解析 PDF 死锁。

> **外部 PDF 引擎**：`opendataloader`（OpenDataLoader，版面分析，需 Java 11+）和 `MinerU`（Go 侧）可作为 PDF 的替代引擎，处理内置解析器搞不定的复杂版面。

## 5. Excel：pandas + 表格摘要

`ExcelParser`（`excel_parser.py`）：

- 用 `pandas` 读取所有 sheet（`read_excel`）；
- **格式修复**：`xlsx_repair.py`（`repair_xlsx_bytes`）修复损坏的 xlsx；`excel_convert.py`（`convert_excel_to_xlsx_bytes` + `engine_for_format`）处理旧 .xls 转换；`xlsx_merge.py`（`fill_merged_cells_xlsx`）填充合并单元格；
- **每行转成结构化文本**：`column: value` 键值对格式，每行一个 chunk；
- **过滤图片函数字符串**：WPS 用 `=DISPIMG("ID",mode)`、Office 365 用 `=_xlfn.IMAGE(url,...)` 嵌入图片，这些被正则 `_IMAGE_FUNC_RE` 识别并排除出文本。

**后续表格摘要**（Go 侧，`DataTableSummaryService`）：

- 用 DuckDB 加载表格（`LoadFromKnowledge`），取样本数据；
- LLM 生成**表格摘要**（表名/核心字段/数据规模/业务场景）和**列描述**；
- 生成 `table_summary` + `table_column` 两个 chunk 建索引，支持「表格检索」和 `DATA_ANALYSIS`（DuckDB SQL 分析）。

## 6. PPT：MarkItDown + LibreOffice

`pptx`/`ppt` 用 `MarkitdownParser`（微软 MarkItDown 库）：

- **现代 .pptx**（ZIP/OOXML）→ MarkItDown 直接转换；
- **旧版 .ppt**（OLE 二进制）→ `ppt_convert.py` 先检测 OLE，用 **LibreOffice（`soffice`）转换成 .pptx**（`normalize_ppt_bytes`），再交给 MarkItDown；
- `pptx_media.py` 提取 PPT 里的媒体（图片等）供 Go OCR/caption。

## 7. EPUB / HTML / MHTML / Markdown / XMind

| 格式 | 解析器 | 逻辑 |
| --- | --- | --- |
| `epub` | `EPUBParser` | `ebooklib` 解析 EPUB 结构 + `BeautifulSoup` 转 HTML → Markdown |
| `html`/`htm` | `HTMLParser` | `BeautifulSoup` 提取正文 → `MarkdownParser` 规范化 |
| `mhtml` | `MHTMLParser` | `email` 解析 MIME + `BeautifulSoup` 转 Markdown |
| `md` | `MarkdownParser` | 直接用；含 `MarkdownTableUtil`（表格格式化）、`MarkdownImageUtil`（base64 图片处理） |
| `xmind` | `XMindParser` | 解压 XMind 归档，解析 `content.json`/XML 的 topic 树 → Markdown 大纲 |

**网页抓取（URL 导入）**单独走 `WebParser`（`web_parser.py`）：用 `playwright`（无头浏览器渲染 JS）+ `trafilatura`（正文提取），不是静态 HTML。

## 8. 图片 / 音频 / 视频

| 格式 | 处理 |
| --- | --- |
| **图片**（jpg/png/...） | `ImageParser` 只返回图片引用；实际 OCR + VLM caption 在 Go 侧的多模态任务（`image:multimodal`）完成 |
| **音频**（需 ASR） | 无内置音频解析器；Go 侧检测 `IsAudioType`，调 ASR 模型转写为文本 |
| **视频** | **不支持**（Go 侧 `ProcessDocument` 直接 `failed`，报「暂不支持视频文件」） |

## 9. 解析引擎（多引擎路由）

来源：`internal/infrastructure/docparser/`（Go 侧引擎目录）+ `docreader/parser/registry.py`（Python 侧解析器注册表）。

解析引擎的选择是**两层**的：Go 侧先选「引擎」（决定解析在哪儿发生、用哪个 reader），Python docreader 侧再选「解析器类」（决定用哪个 Parser 处理这种格式）。中间用知识库级的一条 `ParserEngineRules` 配置串起来。

### 9.1 数据模型：文件类型 → 引擎

`internal/types/knowledgebase.go:234-253`：

```go
type ParserEngineRule struct {
    FileTypes []string `json:"file_types"`  // 匹配哪些格式，如 ["pdf","docx"]
    Engine    string   `json:"engine"`      // 用哪个引擎，如 "mineru"
    XLSXFirstRowAsHeader *bool              // Excel 专属开关
}
type ChunkingConfig struct {
    ...
    ParserEngineRules []ParserEngineRule    // 空 = 全部走默认(builtin)
}
```

### 9.2 引擎目录：两个 registry

**Go 本地引擎**（`engines.go` 的 `init()` 注册 8 个，每个声明自己的 `FileTypes` + `CheckAvailable` + `NewReader`）：

| 引擎 | 解析位置 | 支持格式（节选） |
| --- | --- | --- |
| `builtin` | Python docreader | docx/doc/pdf/xlsx/pptx/epub/html/xmind/图片/音频 |
| `simple` | Go 原生 | md/txt/csv/json/图片/音频 |
| `anydoc` | Go 进程内 | 办公文档（需链接转换器） |
| `weknoracloud` | 云端 API | docx/doc/pdf/xlsx/pptx |
| `mineru` / `mineru_cloud` | MinerU 服务 | pdf/图片/doc/docx/ppt/pptx |
| `paddleocr_vl` / `paddleocr_vl_cloud` | PaddleOCR-VL | pdf/图片 |

**Python 远程引擎**（不注册在 Go 本地，由 `ListEngines` RPC 动态发现；`NewReader` 对未知引擎名直接路由到 docreader 客户端）：

| 引擎 | 支持格式 | 说明 |
| --- | --- | --- |
| `markitdown` | md/pdf/docx/doc/pptx/ppt/xlsx/xls/csv | 微软 MarkItDown 库 |
| `opendataloader` | pdf | OpenDataLoader PDF 版面分析（需 Java 11+） |

### 9.3 选择链路（两层）

```text
上传文件(file_type) / URL
  │
  ├─ 合并 overrides：tenant 级 + upload 级 ParserEngineOverrides
  │     └─ applyParserRuleOverrides + SSRF 校验 URL
  ▼
ResolveParserEngine(file_type)   ← 知识库 ParserEngineRules 匹配，没中 = ""
  ▼
NewReader(engine, fileType, isURL)
  ├─ 命中本地引擎(Go)        → 本地 reader（simple / anydoc / mineru / paddleocr / 云端）
  ├─ engine=="" 且简单格式    → SimpleFormatReader（Go 原生，不经过 Python）
  └─ 其余                    → Python docreader 客户端
       ▼
     Python registry.get_parser_class(engine, file_type)
       ├─ 引擎支持该格式 → 对应 Parser（ExcelParser / MarkitdownParser / ...）
       └─ 不支持         → 回退 builtin
       ▼
     detect_effective_file_type（magic bytes 嗅探，纠正「改名文件」）
```

关键函数：

- `ChunkingConfig.ResolveParserEngine(fileType)`（`knowledgebase.go:284-305`）：归一化 file_type（小写、去前导 `.`）→ 遍历规则找 `FileTypes` 命中项 → 返回 `rule.Engine`；**没命中返回空串 `""`（= 默认 builtin）**。URL 导入按 `"url"` 单独匹配（`knowledge_process.go:3631-3633`）。
- `docparser.NewReader(engine, fileType, isURL, deps)`（`engine_registry.go:69-79`）三分支：
  1. `lookupEngine(engine)` 命中本地引擎 → `registration.NewReader`；
  2. `engine == "" && !isURL && IsSimpleFormat(fileType)` → `SimpleFormatReader`（`md/txt/csv/json/图片/音频` 白名单，`builtin_converter.go:15-43`）；
  3. 其余 → `remoteReader`（Python docreader 客户端）。
- Python 侧 `registry.get_parser_class(engine, file_type)`（`registry.py:59-83`）：请求引擎不支持该格式时**自动回退 builtin**，不会报错。

### 9.4 默认行为与护栏

- **默认（不配规则）**：`ResolveParserEngine` 返回空 → 简单格式 Go 原生处理，复杂格式走 Python `builtin`。
- **想换引擎**：在知识库 `ParserEngineRules` 加一条 `{file_types: ["pdf"], engine: "mineru"}` 即可。
- **两层分工**：Go 的「引擎」决定**在哪解析**（本地/远程 API/Python 服务）；Python 的「解析器类」决定**用哪个 Parser**处理这种格式，带 builtin 兜底。
- **两道护栏**：SSRF 校验（`validateParserEngineOverrideURLs`、`ValidateURLForSSRF`）+ magic-bytes 格式嗅探（`detect_effective_file_type`）。

## 10. 关键设计模式

### 10.1 责任链（FirstParser / PipelineParser）

`chain_parser.py` 提供两种组合模式：

- **FirstParser**：按顺序尝试多个解析器，返回第一个成功的（fallback 链）。例：`Docx2Parser` 的 `_parser_cls = (MarkitdownParser, DocxParser)`（MarkItDown 优先，失败回退 python-docx）；
- **PipelineParser**：串联多个解析器，每个处理前一个的输出（pipeline）。例：`HTMLParser = PipelineParser.create(HTMLToMarkdownParser, MarkdownParser)`。

### 10.2 格式嗅探（magic bytes）

不信任扩展名，检查文件头 magic bytes 纠正「改名文件」（.docx 改名成 OLE 二进制 → 路由到 doc）。

### 10.3 解析 / 分块 / OCR 三层解耦

- **docreader（Python）**：只做「格式 → Markdown + 图片引用」；
- **chunker（Go）**：分块；
- **Go 多模态/ASR**：OCR、VLM caption、语音转写。

这一解耦让格式解析可以独立演进，OCR/VLM 按需异步执行，扫描 PDF 通过「渲染成 JPEG + 打标」把 OCR 推迟到 Go 侧。

### 10.4 统一 Markdown 中间态

所有格式最终都汇入 Markdown，后续的分块、索引、检索、图谱抽取全部只面向 Markdown 这一种输入，新格式只需新增一个 Parser 类 + 注册到 registry。
