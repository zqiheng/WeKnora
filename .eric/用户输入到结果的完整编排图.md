> 每个子图标注了对应源码文件与关联的深度分析文档，细节展开请按图下指引跳转。

## 图 0 · 总图：完整路由与分支

```mermaid
flowchart TD
    U["用户输入：文本 / 图片 / 附件<br/>作用域：@KB · @Tag · @文档 · @MCP · @Skill"] --> E["HTTP 入口<br/>internal/handler/session/qa.go"]
    E --> R{"路由分发（图 1）"}
    R -->|"POST /knowledge-chat/:session_id"| KQ["KnowledgeQA · RAG 快速问答<br/>固定插件流水线"]
    R -->|"POST /agent-chat/:session_id"| AQ["AgentQA · ReAct Agent<br/>LLM 自主编排"]
    R -->|"POST /knowledge-search"| SQ["SearchKnowledge · 纯检索（图 11）"]
    KQ --> PL["流水线装配（图 2）<br/>LOAD_HISTORY → MEMORY_RECALL → QUERY_UNDERSTAND"]
    AQ --> AL["Agent ReAct 循环（图 8）"]
    SQ --> SR["检索结果 JSON 直接返回"]
    PL --> Q{"意图分支（图 3）"}
    Q -->|"kb_search / summarize / clarification"| SCH["检索链：混合检索（图 4）<br/>→ 重排 → 合并（图 5）"]
    Q -->|"web_search 且已开启"| SCH2["检索 + 网页抓取（图 6）"]
    Q -->|"greeting / chitchat / follow_up<br/>image_only / doc_only"| CHAT["跳过检索直答<br/>意图专用 prompt（图 7）"]
    SCH --> TOPK["FILTER_TOP_K 截断"]
    SCH2 --> TOPK
    TOPK --> DA["DATA_ANALYSIS<br/>DuckDB 表格分析（可选）"]
    DA --> CHAT
    CHAT --> STREAM["CHAT_COMPLETION_STREAM<br/>LLM 流式生成（图 7）"]
    AL --> STREAM
    STREAM --> OUT["结果输出通道（图 12）<br/>EventBus → StreamManager → SSE → 前端"]
    OUT -.-> POST["异步后处理（图 12）<br/>标题生成 · 问题推荐 · 记忆沉淀"]
```

**路由全景**：三个 HTTP 端点对应三种模式——固定流水线（RAG）、LLM 自主循环（Agent）、纯召回（检索预览）。RAG 内部再按**意图**分三条支线（KB 检索 / 网页 / 直答）。两种问答模式共用同一套 SSE 输出通道。

关键文件：`internal/router/routes_chat.go`、`internal/handler/session/qa.go`。

## 图 1 · 入口分发路由

```mermaid
flowchart TD
    REQ["HTTP 请求到达<br/>/knowledge-chat · /agent-chat · /knowledge-search"] --> PARSE["parseQARequest / executeQA<br/>解析 query · base64 图片 · 文件附件 · 临时附件"]
    PARSE --> MODE{"qaMode 路由"}
    MODE -->|"qaModeNormal"| RAG["sessionService.KnowledgeQA<br/>session_knowledge_qa.go:23"]
    MODE -->|"qaModeAgent"| AGT["sessionService.AgentQA<br/>session_agent_qa.go:20"]
    MODE -->|"纯检索（无 session）"| SK["sessionService.SearchKnowledge"]
    RAG --> SETUP["setupSSEStream（qa.go:614）<br/>建立 SSE · 创建 EventBus · 订阅事件"]
    AGT --> SETUP
    SETUP --> TITLE["GenerateTitleAsync<br/>异步生成会话标题（可选）"]

    SETUP --> LOOP["handleAgentEventsForSSE<br/>100ms ticker 增量拉取事件"]
    LOOP --> D{"流状态"}
    D -->|"complete 事件"| FIN["发送完成并关闭"]
    D -->|"客户端断开"| RET["优雅退出（生成不中断）"]
```

## 图 4 · 混合检索（CHUNK_SEARCH_PARALLEL 内部）

```mermaid
flowchart TD
    Q["query = RewriteQuery<br/>（实体图谱召回并行，可选 NEO4J_ENABLE）"] --> T["PluginSearch：按 embedding 模型分组<br/>每 KB 并发 → HybridSearch"]
    T --> S1["1. 归一化 MatchCount"]
    S1 --> S2["2. KB 集合 + 鉴权 + 校验 embedding 模型一致"]
    S2 --> S3["3. pickPrimary 选定主 KB"]
    S3 --> S4["4. 过度召回：matchCount = max(MatchCount×5, TopK) × KB 数（上限 500）"]
    S4 --> S5["5. GetQueryEmbedding（仅一次）"]
    S5 --> S6["6. resolveStoreGroups：按（store, 租户）分组绑定检索引擎"]
    S6 --> S7["7. buildRetrievalParams 三分区<br/>FAQ 向量库 / 文档向量库 / 文档关键词库"]
    S7 --> S8["8. retrieveFromStores 并行 fan-out<br/>pgvector / Milvus / Qdrant / Weaviate / ES / OpenSearch / DuckDB …"]
    S8 --> S9["9. classifyRetrievalResults：向量结果 / 关键词结果"]
    S9 --> S10{"10. 两路都有？"}
    S10 -->|"仅一路"| DED["deduplicateByScore 按 chunk ID 去重"]
    S10 -->|"两路"| RRF["fuseWithRRF 融合<br/>rrf = vw/(k+vr) + kw/(k+kr)"]
    DED --> S11
    RRF --> S11["11. applyFAQPostProcessing<br/>FAQ KB 迭代 TopK 召回"]
    S11 --> S12["12. 截断到 MatchCount"]
    S12 --> S13["13. processSearchResults 富化<br/>正文 · 父块 · 相邻块 · 图片 OCR"]
    S13 --> LOW{"召回不足？（结果数小于 EmbeddingTopK）"}
    LOW -->|"是"| QE["query_expansion 查询扩展<br/>去停用词 · 关键词聚焦补召回（无 LLM）"]
    QE --> S13
    LOW -->|"否"| OUT["SearchResult 列表 → 重排（图 5）"]
```

**要点**：核心是「向量 + 关键词」双路召回 + **RRF 融合**；过度召回 5 倍候选池交给重排裁剪；多引擎 fan-out 对上层透明；低召回时本地规则查询扩展兜底。

关键文件：`internal/application/service/knowledgebase_search.go`、`knowledgebase_search_fusion.go`、`knowledgebase_search_storegroup.go`、`knowledgebase_search_fanout.go`。深度文档：《问题检索与QA回答流程》§4、《检索质量深度剖析》、《存储方案与检索引擎架构》。

## 图 5 · 重排 → 合并 → TopK 截断

```mermaid
flowchart TD
    S["SearchResult"] --> R1["getEnrichedPassage<br/>清洗 markdown/URL 噪声 + 拼 caption/生成问题"]
    R1 --> R2["rerankModel.Rerank(query, passages)"]
    R2 --> R3{"阈值过滤：score ≥ RerankThreshold？"}
    R3 -->|"无结果"| R4["阈值降级 ×0.7（下限 0.3）重试"]
    R4 --> R5{"仍无结果？"}
    R5 -->|"是"| R6["top-1 兜底（≥ fallbackMinScore 保一条）"]
    R5 -->|"否"| R7
    R3 -->|"有结果"| R7["composite = 0.6×model + 0.3×base + 0.1×sourceWeight"]
    R6 --> R7
    R7 --> R8["FAQ 提权（可选 FAQScoreBoost）<br/>Wiki 页 ×1.3（WikiBoost 插件）"]
    R8 --> R9["MMR 去冗余（λ=0.7）→ RerankTopK"]
    R9 --> M1["MERGE ① 优先 RerankResult，空则回退 SearchResult"]
    M1 --> M2["② ID + 内容签名去重"]
    M2 --> M3["③ 注入历史轮次引用片段"]
    M3 --> M4["④ resolveParentChunks 子块 → 父块"]
    M4 --> M5["⑤ 按知识源 + 类型分组，合并相邻正文"]
    M5 --> M6["⑥ populateFAQAnswers 填充 FAQ 答案"]
    M6 --> M7["⑦ expandShortContextWithNeighbors 相邻块补足"]
    M7 --> M8["⑧ 再合并 + 去重（含部分重叠）"]
    M8 --> F["FILTER_TOP_K：searchResult 截断到 RerankTopK"]
    F --> O["MergeResult → 组装（图 7）"]
    R2 -.->|"重排失败"| FB["api_error_fallback：直接用检索结果"]
    FB --> M1
```

**要点**：重排有三级兜底（降级重试 → top-1 → 直用检索结果），保证流水线不断；合并阶段做「补全上下文」（父块/相邻块/FAQ 答案），最终送入 LLM 的数量由 `RerankTopK` 硬收敛。

关键文件：`internal/application/service/chat_pipeline/rerank.go`、`merge.go`、`filter_top_k.go`、`wiki_boost.go`。深度文档：《问题检索与QA回答流程》§5-6、《检索质量深度剖析》。

## 图 8 · ReAct Agent 循环（AgentQA 路由）

### 预设 Agent 的路由

| 预设 | 适用场景 | 工具面 | 提示词核心 |
| --- | --- | --- | --- |
| `progressive_rag_agent`（默认） | 只绑普通 KB | RAG 工具集 | Strict Sequence：grep → search → list（MANDATORY）→ graph（可选）→ web（兜底） |
| `wiki_researcher`（维基问答） | 只绑 wiki KB | 只读 wiki 工具 + `wiki_flag_issue` | Search-Read-Expand 循环 |
| `hybrid_rag_wiki_agent`（混合） | 同时绑 wiki KB 和普通 KB | RAG + Wiki 双工具集 | `WIKI_KBS` / `CHUNK_KBS` 分区，明示哪些 KB 走页面、哪些走 chunk |
| `wiki_fixer`（维基修订） | 修复 wiki 问题 | 全量写工具 | 先读 issue 再定修复策略，一轮改完 |

### 全绑定场景（绑定所有 KB + 所有工具）：裁决权交给 LLM

当 `KBSelectionMode=all` 且工具全开时，上图两个硬闸门（RAG 工具 / wiki 工具）**全部放行**——此后没有任何代码级 if/else 再裁决「走 RAG 还是走 wiki」，决策由 LLM 依三层信息作出：

1. **系统提示词（决定性因素）**：
   - 默认 `progressive_rag_agent`：Strict Sequence 只编排 RAG 工具链，**不提 wiki 工具**——wiki 工具虽注册但实际闲置（LLM 只能靠 description 自悟，无确定性保证）；
   - `hybrid_rag_wiki_agent`：为全绑定场景设计的显式路由规则（`agent_system_prompt.yaml`）：
     - 读 `<bound_knowledge_bases>` 的 `capabilities` 属性构造两个内部路由变量——含 `wiki` → 归入 `WIKI_KBS`，含 `chunks` → 归入 `CHUNK_KBS`；
     - **概念性 / 关系性 / 是什么 / 怎么工作 → 优先 wiki**（`WIKI_KBS` 非空时），否则退回 chunks；
     - **具体事实 / 精确引用 / 数字 / 代码级 → 优先 chunks**（`CHUNK_KBS` 非空时），否则退回 wiki；
     - 交叉兜底：chunks 第一轮无结果且 wiki 可用 → 回 wiki 再搜；并禁止把 `capabilities`、`wiki-only` 等内部机制泄露给用户；
   - `wiki_researcher`：Wiki First 绝对规则——凡 wiki 可能覆盖的领域事实必须先查 wiki。
2. **运行时 `capabilities` 属性**：每个绑定 KB 以 `capabilities="wiki,chunks"` 标签进 `<bound_knowledge_bases>`（`prompts.go` 的 `formatKnowledgeBaseList`）；双开 KB 两标签都有、同时出现在两个分区，LLM 按问题性质在同一库的两种表面间选。
3. **工具 description（兜底信号）**：提示词无显式规则时，这是 LLM 唯一的分诊依据——软引导，非保证。

结论：**「何时走 RAG、何时走 Wiki」在全绑定场景下不是系统硬规则，而是 prompt 设计问题**——这正是预置 Agent 类型（`agent_type`）存在的意义：用「推荐的提示词 + 工具白名单 + KB 兼容性提示」打包，在自由度最高的场景下给出确定的路由策略。另外这一切只发生在 smart-reasoning 模式；quick-answer 模式无论绑定多少库，固定管线永远只走 chunk 检索，wiki 页不参与。

### 边界与现状（容易踩坑的地方）

1. **RAG 固定管线从不读 wiki 页**：`/knowledge-chat` 下 wiki 页不参与任何环节；`wiki_boost`（×1.3 重排加权）预埋了「wiki 页进检索」的通道，但创建侧未实现（`wp-` chunk 从没被创建过），实际不触发。
2. **wiki-only KB 在 RAG 管线下检索为空**：`search.go:326-340` 注释明确 wiki/graph-only KB 无向量或关键词索引可降级，HybridSearch 空手而归——这类 KB 只能靠 Agent 的 wiki 工具消费。
3. **双开 KB 有两套表面**：同一 KB 既开 wiki 又开向量/关键词时，源 chunk 与蒸馏页面并存——LLM 靠工具 description 与 `hybrid_rag_wiki_agent` 的分区提示在两者间选路。
4. **问题推荐的 wiki 来源**：答案生成后，开场/追问推荐问题可能从 wiki 页面生成（来源集：精选/FAQ/文档/Wiki/LLM），与问答检索是两条独立通道。

关键文件：`internal/application/service/agent_service.go`（`registerTools` 能力检测与硬性裁剪）、`internal/application/service/chat_pipeline/search.go`（wiki-only 边界）、`chat_pipeline/wiki_boost.go`（未接线的加权）、`internal/agent/tools/wiki_tools.go`、`grep_chunks.go`、`knowledge_search.go`。深度文档：《Agent工具集与工具调用机制》§3、§5-6、《LLM Wiki知识库生成与使用逻辑》§7。
